## 1. 素材本身：这是缺的那块

```
流 0: h264    320x240  yuv420p     ← RGB
流 1: ffv1    320x240  **gray16le** ← 16 位原始深度
```

1378 帧 @30fps = 45.9 s。**RGB 与深度是对齐的**（把人体框画到深度图上，
正好套住那个近端区域）。

**深度是米制的**，两条物理证据：

* 值域上界 **4091 ≈ Kinect v1 default 模式的 4.0 m 上限**
* **fx=262** 对应 HFOV **62.6°**，与 Kinect v1 彩色的 62.0° 几乎重合

**内容**（这段素材的价值所在）：

```
#114 站立行走 → #229 坐床 → #344 躺床 → #459 下床跪地
→ #574 躺床 → #689 地上爬 → #803 坐床 → #918 躺地上
→ #1148 地上起身 → #1263 站立
```

「躺床上」和「躺地上」的躯干**都是水平的** —— 倾角分不开，**只有离地高度能分开**。
这正是之前记「标定不出来所以门关着」的那一项。

## 3. 🔴 失败一：躺在画面里的人检不出（**推翻先前结论**）

先前在 `corner1_low`（**640×480**）上测出躺姿检出 12/15 = 80%，
据此写过「**关键点这一环不用再担心了**」。**这份素材上不成立。**

```
站立  #114   person 置信度 0.91
躺床  #342   **0.000**   （conf 降到 0.1 才出现 0.24）
躺床  #576   **0.000**   （同上，0.18）
躺地上 #918    0.115
起身  #1146    0.197
```

**类别是对的（`person`，不是误分成 `dog`/`bed`）—— 崩的是置信度**，
站立 0.91 → 躺姿 0.00~0.20，**掉了 4~5 倍**，全部落在 0.25 门限下面。
而 `yolo26n`（纯检测）**连 conf=0.05 都看不到人**。

### 3.1 修法（已实现）：把输入放大，**关键是插值核**

> ⚠️ **本节初版写错了主因，这里更正。** 初版写「主因是分辨率」，
> 并拿「原图 320 → 放大到 640」当证据 —— 但那一列用的是 `INTER_CUBIC`，
> 而对比列换了尺寸的同时也换了插值核，**两个变量一起动**，得不出结论。
> 固定 `imgsz=640`、只改插值核重测后，真正的变量才显出来。

固定算力预算（`imgsz=640`，4 个躺姿关键帧的 person 最高置信度）：

```
                      #342   #576   #918   #1032    均值
不放大(内部LINEAR 2x)  0.000  0.000  0.115  0.184    0.075
INTER_AREA            0.000  0.069  0.000  0.099    0.042   ← 最糊
INTER_LINEAR          0.238  0.179  0.301  0.382    0.275
INTER_CUBIC           0.476  0.286  0.407  0.492    0.415
INTER_LANCZOS4        0.531  0.364  0.469  0.460    **0.456**
```

**置信度跟着放大的锐度单调走**，四帧排序完全一致。
三条被排除的做法：

* **`imgsz` 开大不是替代方案。** `imgsz=960` 时 ultralytics 内部用
  `INTER_LINEAR` 放 3×，结果（0.091~0.230）**不如**手工 `INTER_LANCZOS4` 放 2×。
* **内部那步放大确实是 `INTER_LINEAR`** —— 实测它与手工 `INTER_LINEAR`
  **逐帧完全相等**（0.238/0.179/0.301/0.382），这一条把机制钉死了。
* **放大超过 2× 不再有收益**（LANCZOS4 4× 均值 0.449 vs 2× 的 0.456）。
* 附带否掉：「LANCZOS4 + 反锐化掩膜」均值最高（0.474）但**跨帧方差大**
  （帧 576 从 0.364 掉到 0.145），不可靠，不采用。

**已实现**：`g2_core/detector.py` 的 `upscale_min_side`（默认 480）——
短边不足时用 `INTER_LANCZOS4` 整数倍放大再推理，**结果坐标自动还原到原图**。
Kinect 320×240 → 2×；RealSense 640×480 短边正好 480 → 倍数 1，
**行为与改动前完全一致**。

生产链路实测复现（`Detector` 默认配置 vs 关闭放大）：

```
        关闭放大   打开放大   手工实验参考值
#342     0.238     0.531      0.531
#576     0.179     0.364      0.364
#918     0.301     0.469      0.469
#1032    0.382     0.460      0.460
```

逐帧**精确相等**，说明生产路径与上面的实验是同一件事，没有走样。

> ⚠️ 坐标还原漏了**不会报错**：关键点会整体偏到 2 倍远处，去索引深度图时
> 采到的是完全另一个位置，离地高度照常算得出来，只是全是错的 ——
> 与下面「地面拟合锁错平面」是同一类。已有测试 + 变异测试钉住。

> ⚠️ 这与修跟踪器那条**是同一个失效模式**：**关键帧上置信度掉到门限以下 → 静默丢弃
> → 下游永远收不到结论**。那次是跟踪器的 `new_track_thresh`，这次是检测器的 `conf`。
>
> 实际后果：**若 `conf` 是在站立数据上调的（0.25），它会在人躺下的那一刻把人丢掉**
> —— 而躺下正是我们要检测的事件。

关键帧的**关键点离地高度**：

```
站立 114 : 肩 +1.30/+1.33  髋 +0.89/+0.89    ← 正确
躺床 342 : 肩 +0.62/+1.61  髋 +0.61/+0.64    ← 三点在 0.62（床面）✓，右肩是离群
躺地 1032: 肩 -0.00/-0.11  髋 -0.31/-0.40    ← 全在 0 附近，且为负

而**全图高度分布**暴露了真正原因：

```
114 / 342 : 全图中位高度 +0.56 / +0.58   ← 平面在场景底部，合理
1032      : 全图中位高度 **-0.00**       ← **一半画面在拟合平面之下**

**平面根本不在底部** —— 床占据大片视野时，RANSAC 锁到了别的平面。

### 4.1 ⚠️ 更正：帧 1032 那条**不成立**，真正的原因不是地面拟合

按上面同样的口径复算「全图中位高度」（114/342 精确重现了初版的 +0.56/+0.58）：

```
    帧     全图中位高度   相机高   不让下方比
  114        +0.57      +2.44    98.2%
  342        +0.58      +2.45    96.6%
 1032        **+0.55**  +2.41    98.4%   ← 初版记的是 -0.00
```

**帧 1032 的平面是好的**，全图中位高度 +0.55，和其他每一帧一样。
初版那一格 `-0.00` 复现不出来，是当初跑错了。

**所以那个 -0.21 m 不是平面错了，是关键点/取深度那一环错了** ——
而它也不是独立失败：置信度崩 → 关键点落错 → 深度采错位置。

> 这条更正很重要：按初版的判断去「修地面拟合」，会去调一个没坏的东西，
> 而真正坏的那条链一直没人动。

**但「床 vs 地面」这个问题本身仍未验证**，而且原因和初版写的完全不同 ——
见 §4.4。

### 4.2 但真失败是存在的 —— 只是不在 1032 上

不能因为 1032 平反就认为地面拟合没问题。每 5 帧取一帧扫 **276 帧**：

**约 8% 的帧 RANSAC 锁到了天花板/墙**，而原先的代码**没有任何检查**会把它们挡下。
这正是初版担心的那类缺陷，只是发生在了别的帧上。

### 4.3 校验阈值是**被实测改下来的**

初版拍的「≥95% 的点在平面上方」经不起数据：

```
只用相机高度 [1,3]     拒 8.3%
+ 不让下方比 ≥ 0.95    拒 36.2%   ← 初版的值，多拒 28%
+ 不让下方比 ≥ 0.85    拒 13.8%
+ 不让下方比 ≥ 0.50    拒 8.3%    ← 与只用相机高度**完全相同**
```

实测空档是 **[0.193, 0.543]**，而 0.95 落在「正确那一堆的中间」。
被它误杀的帧里有两个有真值可查：

```
帧  229 坐床  被拒  不让下方比 93.7%  → 髋 +0.65 m（= 床面高度，正确）
帧 1263 站立  被拒  不让下方比 92.4%  → 髋 +0.91/+0.91 m（站立正确值）
```

根因是这个比例**测的是拟合精度而不是「是不是地面」**：远处地板上零点几度的
角度误差就能累积出超过 2 cm 的偏差，把点算到平面下方去。
所以它只适合当**灾难性错误的兜底**，阈值取宽；精度问题交给相机高度那条。

**另一个数据集独立证实了这一点。** 在 `corner1_low`（640×480 RealSense，
FX=615，与 Kinect 完全不同的相机）上抽 6 帧：

```
内点 11.4~18.2%   相机高 +1.18~+1.28 m   不让下方比 **89.3% ~ 94.1%**
```

相机高度 1.2 m 完全合理、内点率也正常 —— **但六帧的「不让下方比」全部低于 0.95**。
按初版的阈值，这个数据集**一帧都过不了**。
两个相机、两种分辨率、两套内参上的分布都说明 0.95 定错了。

**已实现**：`g2_core/floor.py`，两条校验 + 明确的状态与中文原因。
`min_above_ratio` 默认 **0.50**（「至少一半的点不在平面下方」），
落在实测空档内。原先 `tools/validate_method_b.py` 里那份**没有校验的** RANSAC
已删除，改用它。

```
    帧     conf  结果

  229 坐床  0.85  被拒：两肩的深度差 0.67 m > 0.40
  342 躺床  0.53  被拒：肩宽 0.05 m 超出粗错兜底区间 [0.08, 1.20]
  576 躺床  0.36  被拒：髋宽 0.05 m 超出粗错兜底区间 [0.05, 1.00]
  689 爬行  0.43  被拒：髋宽 0.01 m 超出
  918 躺地  0.47  被拒：关键点置信度 0.25 < 0.5
 1032 躺地  0.46  被拒：两肩的深度差 0.43 m > 0.40   ← 只超一点点
 1148 起身  0.68  被拒：两肩的深度差 2.21 m > 0.40
 1263 站立  0.84  **通过**：肩 +1.36/+1.41  髋 +0.94/+0.98  倾角 21°
```

**9 帧里只有 1 帧产出观测**，而通过的那一帧数值**完全正确**
（真值：站立肩 ~1.3、髋 ~0.9、倾角 ~0）。

也就是说：**链路算对的时候是对的，问题是它几乎不出结果。**

而这 8 次被拒**不是一回事**，不能一起处理：

* **像真错的**：帧 114 两肩深度差 1.05 m、帧 1148 差 2.21 m ——
  一个成年人的两肩不可能差这么多，多半是远侧肩的关键点落到了身体之外、
  取到了背景深度。
* **可能不该拒的**：帧 342「肩宽 0.05 m」、帧 576「髋宽 0.05 m」。
  人是**侧躺**的，两肩在画面上本来就几乎重合 —— 看关键点实际位置：

  ```
    帧    L肩像素      R肩像素    两肩像素距   深度差
   342  (256.5,139.2) (251.2,125.5)   14.7 px   0.02 m   ← 深度一致，只是视角
   576  (264.8,137.0) (266.7,131.1)    6.2 px   0.25 m   ← 同上
  ```

  深度差只有 0.02 / 0.25 m，说明**两个肩的深度是一致的、没取错**，
  只是侧视造成的**透视缩短**。而「肩宽」这道粗错兜底门区间下限是 0.08 m，
  把这种情况当成了尺度错误。

**所以下一步要定的是质检门的口径**，不是地面拟合：

* 宽度类的门（肩宽 / 髋宽）**必须对视角免疫** —— 侧视下它天然趋于 0，
  用它当兜底会把「侧躺」这类最该检出的人丢掉。深度差那一条没有这个问题
  （342/576 的深度差是 0.02/0.25，都远小于 0.40），**应当以它为主**。
* 阈值 0.40 m 在帧 1032 上只差一点点（0.43）就被拒 —— 边界太紧。
* `min_keypoint_conf = 0.5` 对 320×240 的输入偏高（帧 918 只有 0.25/0.35，
  而那是躺在地上的人 —— 正是要检出的目标）。

> ⚠️ 与跟踪器 `new_track_thresh`、检测器 `conf` 是**同一个失效模式**：
> 门限卡在「目标最有价值的那一类样本」的分布中间，静默丢弃，
> 表现为「倒地事件永远是 0」。这已经是第三次了。

### 4.5 🔴 而且幸存下来的观测，高度是**系统性错的**

把生产链路扫完整个序列（每 5 帧一帧，276 帧）：

```
地面不合格 23 帧 → 只得到 **20 条**躯干观测（≈7%）
倾角 中位 56°  范围 7~147°

躺姿(倾角≥60°) n=9 : 离地高度 中位 **+1.78 m**  四分位 +1.55~+1.85
直立(倾角<30°) n=3 : 离地高度 中位 **+1.32 m**
```

**躺着的人比站着的人还高 —— 这在物理上不可能。**

这一条不需要任何真值就能判错，而它说明的问题很具体：
幸存的观测高度**系统性偏高约 1 m**，且偏得最多的正是躺姿（我们唯一关心的那类）。
唯一数值正确的那帧（1263 站立，§4.4）**恰好不是躺姿**。

**根因指向一个已知的有偏估计**：`sample_depth_near` 取窗口的**近端 5 分位**，
深度**系统性偏近**（这个偏置 §5 记过 —— 它让肩宽被压小 40%）。
在高度上的表现就是：

```
y = (v - cy) · z / fy      z 偏小 → |y| 偏小 → 点看着更靠近相机的高度 → 离地高度被抬高
```

对**躺姿**最致命：躺着的人 y 方向跨度小，同样的深度偏置会把整条躯干整体抬上去。

**所以「离地高度分开床与地面」现在有三个叠加的障碍**（按影响排序）：

1. **取深度的近端偏置**直接把高度抬高约 1 m —— 而床与地面的真实差距只有 0.4 m。
   这一条不解决，双峰不可能出现。
2. **质检门**丢掉 93% 的观测（§4.4）。
3. **fx 未钉死**（§5），它同时决定三维尺度。

> 📌 三条里 **1 是新的、也是最根本的**。前几轮一直在调门限（跟踪器、conf、质检、地面），
> 都在处理「丢掉多少」；而这一条是**留下来的那些也是错的**。
> 好的消息是：挡这类错误只需要「躺姿高度必须低于直立高度」这么一句
> **不需要真值的自检**，而它现在就能判出问题 —— 也就是说这个信号是**已经在数据里的**。
> 本仓库应当把这类「物理序关系自检」当成常规工序，而不是靠人眼看直方图。

## 5. 已知不确定项

* **fx ≈ 262，但有 ~20% 不确定**。根因是**退化**：宽度类测量 ∝ z/f，
  所以「深度单位」与「焦距」**本质耦合**，单靠人体宽度分不开。
  定下来的依据是 FOV 与量程上界这两条物理先验。
* ⚠️ **上一条在新数据上更可疑了**。多数帧里两肩在画面上只隔 **6~33 px**，
  而按 fx=262、z≈1~2 m 反推，0.40 m 的肩宽本应投影成 **50~100 px**。
  差距 2~3 倍，远超关键点噪声。要么 fx 远小于 262，要么这些帧的人体
  确实强烈偏离正面 —— **两者都和「宽度类门限」直接冲突**，
  在把宽度门当兜底之前必须先把这个搞清楚。
* **取深度的约定是个真实的坑**（本轮自己踩了一次）：`sample_depth_near`
  要求无效像素是 **NaN**（`depth_to_meters` 的约定）。若直接把原始 16 位
  除以 1000，无效像素是 **0**，会被当成有效值参与分位数计算，
  **系统性把深度拉近** —— 量出来的高度看着正常，但是错的。
* **关键点离群**：帧 342 右肩深度 1.31 vs 左肩 2.71（打到近处物体）。
  ⚠️ 这一条**已经被深度差门拦下**（Δ=1.40 > 0.40）—— 那道门在这里起作用了。
