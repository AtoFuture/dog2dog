## P0 —— 会导致静默失效或停机

### P0-① `SENDING` 是没有出口的陷阱态：探索**永久停机且不留痕迹**

`g2_core/state_machine.py`（类 docstring 用法 / `on_nav_timeout` 守卫 / `on_exhausted` 守卫）

文档给的用法是**先** `next_command()`（此刻 phase 被置成 `SENDING` 且返回 `SEND_GOAL`），
**再**调 `select()`。于是 `select()` 失败时，文档指定的两条收尾路径都在 `SENDING` 下执行：

* `on_nav_timeout()` 要求 `phase is NAVIGATING` → 返回 `False`，**phase 不动**
* `on_exhausted()` 要求 `phase in (IDLE, PASSIVE)` → **什么都不做，连 anomaly 都不记**

之后 `next_command()` 对 `SENDING` 一律返回 `NONE`。**唯一**的出口是 `on_goal_sent()`，
而它在没选中目标时永远不会被调用。

**实测**（本次独立复现）：

```
NO_CANDIDATE -> on_nav_timeout():  返回 False，phase 仍 SENDING，后续 5 拍全 NONE
NO_FRONTIER  -> on_exhausted():    同上，且 anomalies=[]
对照组（先 on_goal_sent 再超时）:  SENDING -> NAVIGATING -> 超时 -> IDLE   ✓ 正常
```

`NO_CANDIDATE` 不是罕见情形 —— 审核在 400 张随机图上跑出 **256 次**。
任意一次发生在第一拍，G2 **一次目标都发不出去，永久停机，没有任何日志**。
`NO_FRONTIER` 分支则把「探索完成」信号**吞掉**，永远到不了 `DONE`。

> 三处互相矛盾：`state_machine.py` 的注释写「回 IDLE 稍后再试」、
> `tests/test_state_machine.py:199-206` 把这个行为**钉成了规格**（注释写「SENDING 用 send_failed」）、
> 而实现是「卡死」。修之前先定哪个是对的。

### P0-③ 普通检测消息违反契约：发 `0.0` 而不是 `NaN`

`vision_detector/detector_node.py` · `_publish_detection`

设了 `class_name/confidence/pose/stamp/id/source/has_snapshot`，
**唯独没碰新加的 `onset_stamp`/`torso_tilt_deg`/`torso_height_m`** → 每条 `source="coco"`
的消息都带着 float32 默认值 **0.0** 发出去。而契约写死了「非异常类填 NaN」。

`torso_height_m = 0.0` 尤其危险 —— **那正好是「躺在地上」的值**。
`tests/test_fall_message.py` 专门钉过这条（「发 0 等于凭空造出一个最像倒地的数」），
但那条测试只覆盖了异常类路径。

**后果**：G3 按 README 承诺去「在录好的 bag 上重扫阈值」时，绝大多数样本是假的 0，
而两条消息唯一的区别只在 `source` 上。**修复：补两行 NaN。**

### P0-④ 「躯干大多不可用」告警是**死代码**

`detector_node.py:245`

```python
if st["fall_events"] == 0 and st["fall_unusable"] > st["fall_seen"]:
```

`fall_unusable` 只在 `fall_seen += 1`（:464）**之后**才可能自增（:471），
故恒有 `unusable <= seen`，**条件不可满足**。

**后果**：倒地链路最主流的失效模式（深度取到背景 → 躯干不可用，
实测占 74%）**恰恰没有任何自动提示**，只能靠人去读 debug 日志。

### P0-⑤ `fall_tf_fail` 计数器被绕着走 → TF 全失败时**整行日志都不打印**

`detector_node.py:142-148`（初始化）、`:461`、`:239-244`（上报）

`_stat` 初始化里**没有 `fall_tf_fail` 这个键**，而代码用 `.get("fall_tf_fail", 0) + 1`
—— `.get(..., 0)` 本身就是「撞过 KeyError 然后绕过去」的痕迹。

绕过之后：TF 全查不到 → `fall_seen` 恒为 0 → `[倒地]` 那行被
`if self._fall_enabled and st["fall_seen"]` 门住 → **整行不打印**。
运维看到的是「什么都没发生」，和「场景里没人」长得一模一样。

### P0-⑥ 时间戳回退的异常**没有调用方接住**，会掀翻整个感知节点

`g2_core/fall_tracker.py:178-182` 抛出 → `detector_node.py` 无捕获 → `_on_images` 无捕获

`ApproximateTimeSynchronizer` **不保证回调的时间戳单调**（两路 BEST_EFFORT 图像乱序、
rosbag `--loop`、`/clock` 跳变都是现实触发条件），同一个人在两帧里 `track_id` 相同
→ `obs.stamp` 回退 → 抛 `ValueError`。

**rclpy Humble 的 `executors.py` 会在 `spin()` 线程上重新抛出回调异常**，
而 `main()` 只 catch `KeyboardInterrupt` → **倒地与普通检测一起停，进程带 traceback 退出**。

即使在更宽松的实现下，本帧后续所有 detections 也会被丢弃，且因为
`tr.last_stamp` 保留了旧值，**之后每一帧都会继续抛**。

### P0-⑦ G3 的停手广播落在 `SENDING` 窗口 → **永久卡死**，`PASSIVE` 通路完全没走到

`state_machine.py`（`SENDING` 也返回 `CANCEL_GOAL`）+ `on_goal_cancelled` 不接受 `SENDING`

`sending` 窗口是真实存在的：`send_goal_async` 是异步的，而 `select()` 要跑一次全图 BFS。

```
SEND_GOAL → SENDING → (收到 returning) → CANCEL_GOAL → on_goal_cancelled → 仍 SENDING
→ (收到 exploring) → 仍 SENDING → 后续全部 NONE
```

**`PASSIVE`（本项目专为「返航抢占」设计的通路）完全没走到。**
对返航成功率无害，对覆盖率是致命的。

### P0-⑧ `sample_depth_near` 遇到 NaN/inf 坐标**抛异常**，而 docstring 承诺返回 `nan`

`g2_core/projector.py` · 越界检查写在 `int(round(u))` **之后**

```
NaN 坐标:  ValueError: cannot convert float NaN to integer
inf 坐标:  OverflowError: cannot convert float infinity to integer
```

`keypoints_to_torso_3d` 的置信度门只看 `kp[i][2]`，**不看坐标是否有限**。
异常穿过 `_assess_fall`、`_on_images`（检测循环那段没有 try），
**一个非有限的关键点坐标把整个视觉节点带走**。

代价方向正好搞反了：本项目一贯的取向是「宁可丢这一帧，也不能静默错」，
这里是**不静默，直接带走链路**。

## P1 —— 契约违反 / 指标口径错误

### P1-① 人体尺度门的**下限设在了自己测量分布的中位数之上**

`g2_core/anomaly.py` · `SHOULDER_WIDTH_M = (0.25, 0.65)`

喂给它的那条链路（`sample_depth_near` 默认参数）测出的肩宽**中位数就是 0.24 m** ——
下限落在分布**内部**而不是尾部。意味着**超过一半的真样本被门挡掉，是结构性必然**，
不是偶发。这正是报告 §4 里那个「丢弃率 50~71%」的来源。

（附带：`0.25` 同时是**躯干长**的下限，而躯干长实测中位 0.44 —— 同一条边界
用在两个量级差近 2 倍的解剖量上。）

### P1-② 异常类 `pose` 换了代表点口径，**没有进契约表**

`detector_node.py`（`map_point = (s_mid + h_mid) / 2`，即**躯干中点**）

README 规定「代表点语义由 G2 参数控制，**变更必须通知 G3**」，
而异常类完全不理会 `anchor` 参数。该差异只写在 G2 自己的代码注释里，
**没有进 README 的契约表** —— 违反本项目「契约写进 readme」的硬规矩。

同一帧里同一 `id` 还会有两条 `Detection3D`（coco + pose）共用 `(id, stamp)`，
而 03b 明写用 `(id, stamp)` 做外键 —— **这个键不唯一**。

### P1-③ `torso_height_m` 的定义与所有标定数字**不是同一个量**

节点发的是**躯干中点**（肩中点 z 与髋中点 z 的平均）高度，
而文档里所有标定数字都是**髋部**高度。将来按那些数字打开 `fall_max_height_m`
（比如设 0.35），门限对的是另一个量。

### P1-④ `FALLEN_MAX_DEG = 120` 的上界**没传到新判据**

`anomaly.py` 明确写了 120° 上界及其理由（挡掉肩髋弄反造成的假阳性），
但节点的倒地路径**不走** `assess_fall_from_keypoints_3d` —— 它自己算倾角喂给 tracker，
而 tracker 的「已躺平」条件只有 `tilt >= 60`，**没有上界**。
倾角 ∈ (120°, 180°] 一律被当作 LYING。

### P1-⑤ `min_area_m2` 会把真实门洞整簇滤掉，却返回**终态语义**的 `NO_FRONTIER`

`frontier.py` + `explorer.py`。`detect_frontiers` 的 `[]` 把两件事混成一个返回：
① 一个 frontier 都没有；② 有但每簇都小于阈值。`select()` 把 `[]` 直接映射成
`NO_FRONTIER` → `is_complete=True` → `DONE`。

实测：0.25 m² 在 0.1 m/格下 = 25 格，**1 格深的 frontier 条带要 2.5 m 宽才算数**；
真实门洞（1 m 宽 × 1 格深 ≈ 10 格 = 0.1 m²）会被静默丢弃。**直接威胁覆盖率指标。**

### P1-⑥ `fake_goal_server` 在 `hang` 期间**不会抢占**

`_active_handle` 在进入 hang **之前**就被清空（行进循环结束时），
于是 `victim is None` → 不 abort、不计数、不告警。

用 `outcome:=hang` 同时测「G2 超时」和「G3 返航抢占」时，**抢占根本不会发生**，
被抢占的客户端看到的是 `SUCCEEDED` 而不是真 Nav2 会给的 `ABORTED` ——
与假服务器自己立的规矩（「用假服务器测出的结论，只有在假服务器行为忠实时才可信」）冲突。

## 复核中**被推翻**的结论（方法本身的一部分）

审核者会犯错，我自己也会。这几条是查证后**撤回**的：

| 结论 | 谁提的 | 复核结果 |
|---|---|---|
| `Duration(seconds=0.05)` 可能被截断成 0 | 感知层代理（标为「无法确认」） | **否**。容器内实测 `.nanoseconds = 50000000`。代理后来自己找到了 ROS2 源码并主动撤回 |
| 「推理期间 TF 回调被饿死」 | 感知层代理（标为「疑似」） | **否**。`tf2_ros` 自带 `ReentrantCallbackGroup`。代理自己撤回 |
| `depth_to_meters` 的 `invalid = depth == 0` 是测试盲区 | 我的变异测试 | **否，误报**。代码有第二道保险 `np.isfinite(meters) & (meters > 0)`，0 值照样变 NaN —— 变异**语义等价**，存活是正确的 |
| 审核第一轮的「20 个变异漏 14」 | 我的变异测试 | **不可信**。`.pyc` 缓存没失效，改了的代码根本没被加载。用 `python3 -B` 重跑后才是 16/3 |
| 跟踪器参数「只改 `match_thresh` 就够」的**原始消融表** | 我自己 | **基线是错的**（在 0.6/0.25/0.6 上做的）。审核发现后重做，结论不变但过程要记 |

> **变异存活 ≠ 测试有洞。** 必须逐个核实变异是否语义等价。
> 3 个「漏掉」里有 1 个是等价变异。
