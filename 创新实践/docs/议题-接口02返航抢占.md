# 议题：接口 02 的返航抢占缺口

> 提出人：G2 ｜ 日期：2026-09-17 ｜ 状态：**待全队决定**
> 建议在**第一次接口评审**上定，越晚改代价越大。

---

## 一、问题一句话

**G3 发返航点会抢占 G2 在飞的探索目标，而契约里没有 G3 → G2 的停手信号。**

---

## 二、怎么发生的

契约规定返航复用接口 02：

> `baseline/README.md`：「低电量返航走同一个入口：G3 判断电量，发一个回基站的目标点，**复用这条通路，不另开接口**。」
>
> `g3_integration_eval/README.md`：「发 **G1**：低电量返航的 `NavigateToPose`（复用接口 02）。**G2 的探索目标点和你们的返航点走同一个入口**。」

于是两条 goal 打**同一个 action server**，而 Nav2 一次只接受一个：

```
时间轴 ──────────────────────────────────────────────────────▶

G2  ──发 frontier 目标──▶ [在飞] ────────────────────────────
                              ✗ 被抢占
G3  ──────────────────────发返航点──▶ [在飞] ──▶ 到家 ✓
                                        ✗ 又被抢占
G2  ──────────────────────────────发下一个 frontier 目标──▶
```

**G2 的状态机里没有「被抢占」这个分支**（见 G2 计划 §4.3⑤）。
按现有设计，被抢占会走进「失败 → 拉黑该点 → 选下一个目标」，于是：

1. G3 的返航点被抢占，机器人掉头继续探索
2. G2 再被抢占，再重发
3. 两边反复打架，**机器人回不了家**

**直接威胁项目指标「返航成功率 100%」**（`选题与规划.md` §五）。
而且这不只是指标问题 —— 电量耗尽时狗停在半路，是实打实的设备风险。

---

## 三、为什么不能靠 action 层自己解决

我们查了这个 action 的**实际定义**（ROS2 Humble，容器内 `ros2 interface show`）：

```
#result definition
std_msgs/Empty result        ← 空的！没有 error_code，没有任何状态字段
```

客户端能拿到的只有 `GoalStatus`：`SUCCEEDED` / `ABORTED` / `CANCELED`。

**问题在于「导航失败」和「被人抢占」在 Nav2 里很可能都表现为 `ABORTED`** —— 结果里没有可区分的信息。

**已用探针实测**（`vision_explorer/preemption_probe.py`，可复跑）：

```
A 发出 -> ENTER  [G2 的探索目标]
B 发出（模拟返航抢占）
  A 终态 = ABORTED          ← 被抢占的一方
  B 终态 = SUCCEEDED
```

被抢占的一方收到的是 **ABORTED**，与「导航失败」的终态**一模一样**。

> ⚠️ **结论的边界**：这次是在 `fake_goal_server` 上跑出来的，而假服务器的抢占行为
> （abort 旧目标）是我们**对 Nav2 的建模**。它验证了「被 abort 的客户端确实看到 ABORTED」
> 这条链路，但**不能替代对真 Nav2 的验证**。
> 等 G1 的 Nav2 起来后，把这个探针对着真服务器再跑一次即可（命令不变）。
> 不过无论真 Nav2 给的是 ABORTED 还是 CANCELED，只要它和「导航失败」用同一个终态，
> G2 就无法区分 —— 这个结论是稳的。

**结论：不能让 G2 靠 action 返回值去猜自己是不是被抢占了。**

（补一句：把返航改成**独立 action** 也解决不了 —— 底层还是同一个 Nav2 导航栈，
一个机器人同一时刻只能走一个目标，抢占只是换个地方发生。**问题本质是需要协调，不是需要新通路。**）

## 四、三个候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. G2 自己看电量** | G2 订阅 `/battery_state`，低于阈值自行进入 PASSIVE | 不需要新接口，改动最小 | G2 得猜 G3 的阈值；两边的阈值一旦不一致，会出现「G2 已停但 G3 没发返航」或反之。**语义是隐式的** |
| **B. G3 提供停手信号** ⭐ | G3 发布任务状态，G2 订阅，非「探索」态即 PASSIVE | 语义明确、可测试；**架构上也对** —— 任务状态本来就该由 G3 拥有（G3 的 README 已规划「状态机：待机 / 探索 / 返航 / 急停」） | 需要新增一条接口（这正是接口评审该做的事） |
| **C. G2 从 action 结果推断** | 非自己发起的 abort 就转 PASSIVE | 零新接口 | **第三节已说明不可行** —— 分不清「失败」和「被抢占」。若强行用，会把正常导航失败也误判成 PASSIVE，导致探索永久卡死 |

---

## 五、G2 的建议：方案 B

具体提议（**最小形态**，字段可再议）：

```
# G3 → G2，话题 /mission_state，QoS: transient_local（晚启动的 G2 也能拿到当前态）
std_msgs/String   state    # idle | exploring | returning | estop
```

G2 侧的行为：

```
state != "exploring"  ──▶  进入 PASSIVE：不再发新目标，并主动 cancel 在飞的目标
state 恢复 "exploring" ──▶  回到 IDLE，重新开始选 frontier
```

**为什么选 B 而不是 A：**

1. **语义显式** —— G2 不需要猜 G3 的意图，也不需要知道电量阈值是多少
2. **覆盖的不只是低电量** —— 还顺带解决了「**急停**」场景。G2 现在的设计里，
   急停时它会继续发探索目标，这是个比低电量更危险的问题。方案 A 完全覆盖不到
3. **与 G3 既有的规划一致** —— G3 的 README 本来就规划了这个状态机，
   只是没说要对外发布。发布出来成本极低
4. **可测试** —— G2 的 `fake_goal_server` 可以直接模拟这个信号，
   不需要真机、不需要电量真的掉下去

**为什么不用 A：** 阈值耦合是会出事的。G3 按自己的策略判断「该返航了」，
G2 按自己的阈值判断「该停手了」，两套逻辑一旦漂移就会出现危险窗口 ——
而这种 bug 只在电量真低的时候才暴露，测试很难覆盖。

---

## 六、需要决定什么

1. **是否立这条接口**（方案 A / B / C 选一个）
2. 若选 B：**话题名、消息类型、QoS**（G2 建议 `transient_local`，否则 G2 晚启动会漏掉当前状态）
3. **状态集合是否够用** —— G2 建议至少要有 `estop`，不只是返航
4. **G2 在 PASSIVE 下要不要主动 cancel 在飞目标** —— G2 建议要，否则要等 Nav2 超时
