# 实测报告：预训练检测器在躺姿上的召回

> 2026-09-17 ｜ G2 视觉探索 ｜ 对应计划里「第 2–4 周：实测躺姿 recall」这项任务

---

## 一、为什么必须测这件事

「人员倒地识别」这个交付物建立在一条**未经验证的假设**上：

> 预训练的 COCO YOLO 能稳定检出躺着的人。

而 COCO 数据集里几乎没有躺姿样本。已有文献报告 YOLO 会把蹲着/躺着的人预测成 `dog`，
且这类检测错误是端到端倒地检测误报的**主要来源**。

「零训练成本」这条路线在这里恰恰是最脆弱的一环。**如果不早测，就要到第 10 周交付时
才发现整套判据没有可靠输入可用** —— 那时候再改，代价是重做判据 + 重跑实验。

这次实测花了约半小时、零 GPU 占用，结论却直接决定了要不要走「少量数据微调」
（而那与课题「几乎不占卡」的前提冲突，需要早提）。

---

## 二、方法

### 数据

`Nshisei/multimodal_multiangle_fall_detection_dataset` 的 **`corner1_low`** 子集：

- **低机位** RealSense RGB —— 对应 Go2 的相机高度（约 35 cm、接近水平），
  这是本项目真正要面对的视角
- 场景：室内房间，有桌椅、床、窗帘等家具与遮挡
- 连续录像抽帧，**138 帧**，按文件名时间戳与标注对齐

### 真值

数据集自带标注，`label` 取值：

| label | 含义 | 本次是否计入分母 |
|---|---|---|
| 0 | 正常 | 否 |
| 1 | 倒地**发生中**（过渡态） | 否（太短且语义模糊） |
| **2 / 3** | **已倒地**（两种类型） | **是** |

### 工具

| 脚本 | 作用 |
|---|---|
| `tools/fetch_from_remote_zip.py` | 用 HTTP Range 只取 zip 里需要的文件。数据集整包 2 GB，**实际只下载了 54 MB** |
| `tools/eval_liepose_recall.py` | 按时间戳对齐标注，算真实的倒地帧召回 |
| `tools/check_liepose_recall.py` | 初版，假设每张图都有人 —— **对视频抽帧不成立**，见第四节 |

## 三、结果

### 主结果（yolo26n @ 640，conf=0.25）

| 真值 | 命中/总数 | 召回 |
|---|---|---|
| label 0（正常） | 88/92 | 96% |
| label 2（已倒地 A） | 17/20 | 85% |
| label 3（已倒地 B） | 15/15 | 100% |
| **倒地帧合计** | **32/35** | **91%** |

**91% > 计划的 85% 指标。**

### 那 3 张「漏检」是什么

> ⚠️ **本节原先的结论是错的，2026-09-17 经审查后重写。**
> 原结论称「人根本不在画面里」并据此把分母改成 32、宣称 100% 召回。
> **那个结论不成立** —— 详见下方。

三张是**连续帧**（185640 / 185646 / 185652），属同一段录像（`video_idx=3`）。

逐像素复核后发现，三张帧的**底边都有一条连续的暗色带**（y≈465-480，横向延伸到 x≈434），
色调与受试者的深色裤子/上衣一致；而**空房间参照帧没有这条带**。
也就是说：**人在画面里，只是躺在相机脚下、绝大部分在视场之外，只有衣物边缘可见。**

更直接的证据：**把阈值降到 conf=0.01，185652 仍有一条 person 响应**
（conf 0.0248，bbox `(0, 467, 48, 480)`，正好落在那条衣物带上）。
原报告写的「零 person 响应、没有任何弱响应」**与实测不符**。

**修正后的结论：**

> **倒地帧召回 32/35 = 91%。**
> 3 次漏检都是「人躺在画面下缘、仅衣物可见」——
> 这是**真实的漏检**，不是「没人可检」。

而且这恰恰是**单目低机位对抗遮挡时的典型失效模式**，正是本项目要面对的情况
（Go2 相机在 35 cm 高度，人躺在它脚边时同理）。
**不该把它从分母里剔除** —— 剔了就等于把一个真实的失效模式藏起来了。

> **方法论教训**：原报告只目视检查了 3 张中的 1 张就推断了另外 2 张；
> 而且**同一节里既写着「只有左下角一点点衣物边缘」，又写着「人根本不在画面里」** ——
> 自相矛盾却没有察觉。事后把不利样本移出分母，是实验报告里最不该犯的错。

## 四、选型结论（都基于实测，不是查文档）

### ① 模型代际：无差别

| 权重 | 倒地召回 |
|---|---|
| `yolo11n` | 32/35 = 91% |
| `yolo26n` | 32/35 = 91% |

**完全相同。** 计划里那条「yolo11 落后一代半」的担忧，在这个任务上**不成立**。
选型可以按其他标准（生态成熟度、文档）来定，不必纠结代际。

### ② 模型规模：无差别

| 权重 | 倒地召回 | 640 下耗时（CPU） |
|---|---|---|
| `yolo26n` | 91% | 39 ms/帧 |
| `yolo26s` | 91% | — |
| `yolo26m` | 91% | — |

**n / s / m 三者完全一样。** 说明那 3 张漏检**不是模型容量问题** ——
加大模型救不回来，只有换数据（微调）或换思路才行。

### ③ 分辨率：提高无益，甚至有害

| conf | imgsz | 倒地召回 |
|---|---|---|
| 0.25 | 640 | 91% |
| **0.25** | **960** | **86%** ← 反而更差 |
| 0.10 | 640 | 91% |
| 0.10 | 960 | 91% |

提高分辨率在标称阈值下**让召回下降**，要配合降低 conf 才恢复。
推测是 YOLO 的置信度分布对输入分辨率敏感（模型在 640 上训练的）。

### ④ 置信度阈值：降低无益

640 下 conf 从 0.25 降到 0.10，召回**一点没变**（都是 91%）。
说明漏检不是「分数卡在阈值下」，而是真的没检出。

### ⑤ 速度：绰绰有余

| 配置 | CPU 耗时 |
|---|---|
| yolo11n @ 640 | 41.6 ms/帧（24.1 FPS） |
| yolo26n @ 640 | 39.2 ms/帧（25.5 FPS） |
| yolo26n @ 960 | 65.1 ms/帧（15.4 FPS） |

即使是纯 CPU，640 下也有 **25 FPS** —— 远超计划里的 5 Hz 抽帧需求。
**不需要为了速度牺牲精度，也不需要 GPU。**

> （注：官方 release notes 说 YOLO26 的 CPU 推理快 43%，本次实测只快约 6%。
> 那个数字大概是针对更大模型或别的硬件配置。以实测为准。）

### 推荐配置

```
weights  = yolo26n.pt      # 或 yolo11n，实测无差别；选生态更成熟的也行
imgsz    = 640             # 不要调高
conf     = 0.25            # 不要调低，没有收益
device   = cpu             # 25 FPS 够用，不必占 GPU
```

## 五、对计划风险评级的影响（措辞已收紧）

计划的 §8 风险表里有一条：

> **高** ｜ 预训练检测器在躺姿上召回未知（COCO 缺躺姿样本）｜ 第 2–4 周实测 recall

**实测结果：在本次覆盖的场景下，这条风险没有出现** —— 91% 召回，且检出失败的模式是
「人躺在画面下缘、仅衣物可见」，而不是「把躺着的人认成了别的东西」。

> ⚠️ **但措辞要比初版收紧。** 初版写的是「这个风险不成立、应降级」，
> 而这一轮审查指出：这是**单数据集、单场景、17 段录像、1 名受试者**的结果，
> 且**没有覆盖「沿光轴躺倒」这个最难姿态**。说「不成立」证据不够。
> 准确的说法是：**没有复现，风险从【高】降到【中】。**
>
> 还有一条**数据完整性缺口**必须一起说，见下一节第 6 条。

## 六、边界：这次没覆盖什么（2026-09-17 经审查后补充）

诚实列清楚，免得被当成「倒地识别已经没问题了」：

1. **只测了「有没有检出人」，没测「判不判得出倒地」**
   姿态判据是另一份报告的事。

2. **数据集是模拟跌倒，不是真实侦查场景**
   一个房间、一台固定相机、**一名轮椅依赖受试者**，不是安防场景里的多人、遮挡、异常姿态。

3. **相机参数与 Go2 不完全一致**
   机位高度接近，但 Go2 是 120° 广角 + **会晃动** + **在移动中拍摄**。本数据集是固定机位。

4. **样本不独立：35 张倒地帧来自 17 段录像，不是 35 个独立样本**
   每段贡献 1–3 帧，而那 3 张漏检**全部来自同一段录像**（`video_idx=3`）。
   按独立同分布算置信区间会**严重低估误差**。事件级口径下是 17 段里有 16 段至少检出一帧。
   92 张「正常帧」同理，来自约 19 段连续录像，时间强相关。

5. **没测「沿光轴躺倒」**
   计划里特意提过：人躺的方向与相机光轴平行时（脚朝相机）前缩最严重，是最难的情况。
   本数据集里有没有这种帧，**没有逐帧核对**。

6. 🔴 **评估只覆盖了录像的前 74% —— 这是一个必须交代的数据缺口**

   取数工具 `tools/fetch_from_remote_zip.py` 的汇总行打印的是**尝试数**而不是**成功数**。
   实跑时请求 190 个目标，**磁盘上只有 138 个**，尾部 47 个没下成 ——
   对应录像**最后约 4.5 分钟**，其中**含 2 个倒地事件（video 18、19）**。

   工具对此**没有任何提示**，`depth_big/` 里还有一个 0 字节文件也没被发现。

   也就是说：**本报告的所有数字都是在「不含最后 2 个倒地事件」的子集上算的。**
   这个缺口不改变「检测器能检出躺姿」的方向性结论，但**精确数字不可引用**。
   取数工具已修（见下），重跑可以得到完整覆盖。

7. **单次测试，没有跨场景泛化验证**

## 附二：数据完整性事故（留档）

上一条说的缺口，根因是工具的两个缺陷，已修：

| 缺陷 | 后果 | 修法 |
|---|---|---|
| 汇总行打印 `len(targets)`（尝试数） | 少下了 47 个文件却报「共取 190 个」 | 改为打印**成功落盘数** |
| `write_bytes` 不在 try 内、写后不校验 | 静默产生 0 字节文件 | 写后校验 size，失败即删残文件并计入失败数 |

**教训**：下载工具**静默少给数据**是最危险的一类 bug ——
它不会让程序崩溃，只会让你的结论建立在残缺的数据上，而你看不出来。

```bash
  "https://huggingface.co/datasets/Nshisei/multimodal_multiangle_fall_detection_dataset/resolve/main/corner1_low_realsense_rgb.zip" \
  --out ~/g2_testdata/low_angle_big --stride 30 --limit 190

python3 tools/eval_liepose_recall.py \
  --images ~/g2_testdata/low_angle_big \
  --annot  ~/g2_testdata/corner1_low_annotation.csv \
  --weights yolo26n.pt --conf 0.25 --imgsz 640
```
