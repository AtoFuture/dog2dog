# 实测报告：长宽比判据（方法 A）在低机位下不成立

> 2026-09-17 ｜ G2 视觉探索
> 上一篇：[`躺姿召回实测报告.md`](躺姿召回实测报告.md)（检测「有没有人」）
> 本篇：检测「人是不是倒地了」—— 交付物 3 的真正验收口径

---

## 一、结论先行

**方法 A（检测框长宽比）在低机位下无法区分站立与倒地。**

在计划的判据（归一化高宽比 < 0.6 判倒地）下：
**倒地召回仅 43%，即漏掉了 57% 的真实倒地。**

这不是阈值没调好 —— 扫描了 0.4 到 1.2 **全部阈值**，
**没有任何工作点**能同时满足「检出率 > 85%、误检率 < 10%」。

> ⚠️ **两个必须分开的失败来源**（2026-09-17 审查后补充）：
>
> 35 张倒地帧里，**有 3 张是「根本没检出人」**（见第一篇报告：人躺在画面下缘、仅衣物可见），
> 与长宽比判据**无关**。剔除这 3 张后：
>
> | 口径 | 数字 |
> |---|---|
> | 端到端召回（含检出失败） | 15/35 = **43%** |
> | **在"已检出人"的帧上，判据的准确率** | 15/32 = **47%** |
>
> 也就是说：**即使检测器完美，长宽比判据本身也只有 47% 的准确率。**
> 结论不变（判据不可用），但两个数字要分开说 —— 否则会把检测的账算到判据头上。
>
> ⚠️ 另一处：原版称「扫描了 -20° 到 +20° 的全部俯仰角归一化」，
> 这**不是一条独立维度**（`cos` 是偶函数，±20° 输出逐字相同；
> 且除以 cos(θ) 等价于把阈值重标定 6%）。见 §二 末的说明。

| 阈值 | 倒地召回 | 正常帧误报 |
|---|---|---|
| 0.6（计划采用） | **43%** | 0% |
| 0.9 | 49% | 12% |
| 1.0 | 69% | **27%** |
| 1.2 | 83% | **60%** |

要么漏一半，要么误报六成。**没有中间地带。**

## 二、证据：阈值扫描（§一节那张表就是证据）

> ⚠️ **本节原先给的证据是错的，2026-09-17 经审查后重写。**
> 原版用脚本输出的一个「重叠度」单点统计来论证「两类分布严重重叠」，
> 但那个指标**既没有判别力、输出还与我的叙述相反** —— 详见下方「附：被撤掉的证据」。

**有效的证据是 §一 的阈值扫描表本身**：判据要能用，必须存在一个阈值
**同时**满足「召回 > 85%」与「误报 < 10%」。扫遍 0.4~1.2，**一个都没有**。

换个角度看同一件事 —— **给定误报上限，能达到的最大召回**：

| 误报上限 | 能达到的最大召回 |
|---|---|
| 0%（不容忍误报） | **43%** |
| ≤ 10% | **49%** |
| ≤ 30% | 69% |
| ≤ 60% | 83% |

**这张表才是结论的依据**：想要 85% 的召回，就得接受 60% 的误报；
想把误报压到 10% 以内，召回就掉到 49%。

参考：样本级 AUC(比率↓=倒地) ≈ 0.82，单看这个数字像是「可用」，
但**帧级决策要求在固定阈值下同时满足召回与误报**，
AUC 高不能替代工作点的存在性 —— 这正是单点统计会误导人的地方。

俯仰角归一化救不了：它的修正是除 `cos(θ)`，20° 也只差 6%，
而差距是 43% 召回 vs 83% 召回的量级。

> ⚠️ **另外要说明**：`--pitch-deg` **不是一条独立的扫描轴**。
> `cos` 是偶函数，所以 `+20°` 与 `-20°` 输出**逐字相同**；
> 而且「除以 cos(θ)」等价于「把阈值乘以 cos(θ)」——
> ±20° 只是把阈值轴重标定了 6%。
> 原版报告把它列为「扫描了全部俯仰角」，**夸大了搜索的充分性**。

### 附：被撤掉的证据（留档）

原版 §二 引用了脚本自动打印的这句：

```
正常样本中，有 4% 的比率低于倒地样本的中位数
  区分度尚可，长宽比可作粗筛用。      ← 与「严重重叠」的叙述相反
```

**报告的核心证据与它自己的工具输出相反，当时没有察觉。**

那个指标（`below = (norm_arr < median(fall_arr)).mean()`）没有判别力的原因：

- 它**只测一个方向**（正常样本低于倒地中位数的比例），完全不看召回；
- 它对应的真实工作点是 **召回 ≈ 50%** ——
  「4%、区分度尚可」和「漏掉一半倒地」描述的是**同一个工作点**；
- 「0.25 算严重」这个阈值没有任何依据。

**教训**：单点统计量不能替代**可达工作点的存在性检验**。
判据能不能用，要看「有没有一个阈值同时满足指标要求」，而不是「两类的中位数差不差得开」。

## 三、为什么会这样

### ① 低机位的前缩（这是主因，且对我们的项目同样成立）

相机在 35 cm 高度、接近水平。人躺在地上时：

- **横躺**（身体垂直于视线）→ 投影又宽又扁，长宽比低 ✓
- **纵躺**（身体沿光轴，脚朝相机）→ **极度前缩**，投影可能接近方形甚至偏高 ✗

计划里点名的「沿光轴躺倒」是最难的情况，实测确认它在样本里占了相当比例。

### ② 这个数据集的「正常」类别里混进了低姿态

> ⚠️ **本小节原版依据有误，2026-09-17 修正。**
> 原版称「数据集 README 说明 `usual` 里包含坐在轮椅上的姿态」——
> **README 里没有这句话**（它只说受试者是轮椅依赖者，未说 `usual` 含坐姿）。

实测（审查员逐帧查看全部 35 张倒地帧与多张正常帧）后发现的**真实混淆**是：

- `usual` 类里包含**蹲、跪、坐在地上**等低姿态（例如 185657、190002 帧人蹲在地上却标 usual）
- 而 `label 2` 里也有多帧是**四肢撑地爬行/跪起**（185721、190432、190438、190512）

也就是说，**「蹲/跪/爬到一半」同时出现在两类里** —— 这比「轮椅坐姿」严重得多，
而且方向是让方法 A 显得**更差**（误报分母被污染）。

> 对我们的项目的意义：侦查场景里同样会有人员蹲下、弯腰、坐在地上。
> 所以**这个混淆不是数据集特有的**，它在本项目里也存在。

**不过仍要承认**：本数据集的两类边界比我们的场景**更模糊** ——
它要分的是「轮椅使用者倒地 vs 其日常低姿态」，
而我们要分的是「站着的人 vs 躺在地上的人」，后者视觉差异更大。
所以**方法 A 在我们场景下未必失败得这么"彻底"** ——
但也**没有任何理由相信它够用**，尤其低机位 + 前缩这两个因素同样存在。

## 四、对计划的影响：方法 B 从「加固」变成「必需」

计划 §4.4 原设计是：

```
方法 A（长宽比） 快速粗筛  →  方法 B（三维姿态）确认
```

这个设计**成立的前提是 A 能把大部分真阳性筛出来**。实测证明它筛不出来 ——
在误报为 0% 的阈值下它丢掉 57% 的真阳性。**A 不能做筛子，它会把信号一起扔掉。**

**修正后：**

| | 原计划 | 修正后 |
|---|---|---|
| 方法 A | 粗筛（必做） | **降级为辅助信息**，只作为日志/可视化参考，不参与判定 |
| 方法 B | 确认（做） | **唯一的判据** |

## 五、方法 B 的验证在哪儿做

> 🔴 **本节原先的论断是错的，2026-09-17 经审查后重写并撤回。**
>
> 原版称「该数据集的 RGB 是 1024×1024，深度是 480×640，两者视场不一致
> （RGB 被裁剪过），且没有裁剪参数，**所以方法 B 只能去仿真里验**」。
>
> **实测：`corner1_low_realsense_rgb.zip` 里的图全部是 640×480**，
> 与深度 `480×640` 一一对应，视场吻合。
> 审查员把同一时刻的两路并排渲染，桌/轮椅/床/地板的几何**逐一对齐**。
>
> 「1024×1024」是**另一个数据集**（`laying/`，那张 CCTV 俯视鱼眼图）的分辨率 ——
> 我把两个数据集搞混了，并据此做了一个**不该做的决策**。

**修正后的判断：**

真正的障碍只是**数据集没有提供相机内参**（`CameraInfo` 那份数据没有随包发布）。
而这是个可以处理的障碍：

- RealSense D435i 的默认内参是公开的，可作**粗验**（够判断「方法 B 方向对不对」）
- 也可以从图像自行标定，或直接用深度图里的平面结构反推
- 真正要精确标定时，Lab 的真机标定流程本来就要做（G1 第 9–11 周）

**所以方法 B 应该两边都做，各有各的用处：**

| | 数据集 | 仿真 |
|---|---|---|
| 能做什么 | **快速粗验**：方法 B 的方向对不对、比方法 A 好多少 | **精确定量**：内外参/TF/地面全已知，可真值 |
| 优势 | 真实数据、真实噪声、真实遮挡 | 可**定向构造**最难姿态（沿光轴躺倒、远距离、强遮挡） |
| 何时 | **现在就能做** | 等 G1 的 gz-sim 可用 |

**所以不改建议，但改理由**：仿真仍是做**精确定量验证**的正确场所
（因为它能给真值、能构造边界情况）；但**不该拿「数据集做不了」当理由** ——
那是我判断失误，数据集本来就能做粗验，而且现在就能做。

---

### 附：这个错误是怎么发生的（留档）

1. 我先在 **CCTV 俯视数据集**（`laying/`，1024² 鱼眼）上做了第一次检测测试
2. 后来换到 **低机位 RealSense 数据集**（`corner1_low`），**没有重新确认分辨率**，
   沿用了「这个是 1024²」的印象
3. 看到深度是 480×640 就断定「视场不一致」，**没有实际去核对 RGB 的真实尺寸**

**教训**：换数据集时，**把尺寸、内参、时间戳这些基本属性重新核对一遍**。
跨数据集的经验不能沿用 —— `im.shape` 一行代码就能问的事，我靠印象下了结论。

## 六、这次实测确认与推翻的东西

| 项 | 结论 |
|---|---|
| 预训练检测器能否检出躺姿的人 | ✅ **能**。倒地帧召回 **91%（32/35）**，3 次漏检是「人在画面外沿」而非认错类别（见上一篇） |
| 模型代际 / 规模 / imgsz / conf 是否影响检出 | ❌ 都不影响，用最小的 `yolo26n @640` 即可 |
| **长宽比能否判倒地** | ❌ **不能**。低机位下漏 57% |

坏消息是判据要重做；**好消息是判据的输入是可靠的** ——
检出这一步没问题，问题只出在「拿到框之后怎么判」。
而方法 B 的输入（关键点 + 深度）在真机上都是现成的。
