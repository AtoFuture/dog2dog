# G2 · 视觉探索 — 技术框架规划

> 目标检测 · 三维定位 · 探索决策 · 异常识别
> 本文是 G2 的内部技术方案，接口部分以 `baseline/README.md` 的接口契约为准。

---

## 一、职责边界

**一句话：只决定「去哪」，不碰「怎么走」。**

```
        G2（决策层）                      G1（执行层）
  frontier / 信息增益  ──发目标点──▶   Nav2 路径规划
  「下一片没探过的区域」               代价地图 / 绕障 / TF / 路径
```

边界划清楚，两组才能并行开工、各自独立调试：

| G2 负责 | G2 **不碰** |
|---|---|
| 目标检测、三维坐标解算 | 路径规划、代价地图配置 |
| 选下一个探索目标点 | TF 树的维护与发布 |
| 异常识别 | 避障、恢复行为 |
| 发布 `Detection3D` | 底盘控制、DDS 通信 |

**关键推论**：G2 可以**完全不等 G1**。假 TF + 假地图 + 离线图片就能把全部逻辑跑通，这是本组最大的进度优势，务必用足。

## 二、系统数据流

```
      输入（来自 G1 / 相机）                    G2 内部处理                        输出
 ┌──────────────────────┐         ┌──────────────────────────────┐
 │ OccupancyGrid        │────────▶│ ① frontier 检测               │
 │ (栅格地图)            │         │ ② 可通行性筛选                 │
 └──────────────────────┘         │ ③ 信息增益评分                 │──────▶ NavigateToPose
                                  │ ④ 目标点选择与状态机            │        (→ G1)
 ┌──────────────────────┐         └──────────────────────────────┘
 │ RGB 图像              │──┐
 └──────────────────────┘  │      ┌──────────────────────────────┐
 ┌──────────────────────┐  ├─────▶│ ⑤ YOLO 检测                   │
 │ 深度图                │──┤      │ ⑥ 三维坐标解算                 │──────▶ Detection3D
 └──────────────────────┘  │      │ ⑦ 异常识别（姿态）             │        (→ G3)
 ┌──────────────────────┐  │      └──────────────────────────────┘
 │ TF: map→camera       │──┘
 └──────────────────────┘

        ▲                                                              ▲
        └──────────────── 依赖 G1，但可用假数据先行 ────────────────────┘
```

两条数据流**互相独立**：探索链路（左）只吃地图，感知链路（右）只吃图像。任一链路被阻塞不影响另一条 —— 建议按两条链路并行走，别串成一条。

## 三、模块分解

### 3.1 目标检测

**选型：`ultralytics` 最新版 + COCO 预训练 80 类权重，零训练成本。**

这是选这个课题的核心原因之一，不要自己训检测器。

#### 关键设计点

**① 模型尺寸分档**（等 G3 设备盘点结果定）

| 档位 | 模型 | 用途 | 说明 |
|---|---|---|---|
| 开发/验证 | `yolo11l.pt` | 离线图片、开发机 | 先确认「能不能检出」，不纠结速度 |
| 仿真 | `yolo11m.pt` | gz-sim | 仿真机通常有显卡 |
| 真机（有 Orin） | `yolo11s.pt` | 机载 | 导出 ONNX/TensorRT |
| 真机（无算力，回传） | `yolo11n.pt` | 回传后处理 | 配合抽帧 |

**先按最大的跑，确认效果上限，再逐步往下砍。** 反过来做会分不清「检测器不行」还是「模型太小」。

**② 抽帧，不是每帧都推**

相机 30 Hz，检测不需要 30 Hz。策略：
- 固定抽帧到 **5 Hz** 推理
- 配 **ByteTrack 跟踪**（ultralytics 内置，`model.track()`）—— 帧间复用轨迹，中间帧用跟踪结果补齐
- 这样既省算力，又天然解决「同一个人被连续检出 N 次」的重复上报问题

**③ 类别关注范围**

COCO 80 类里与侦查场景相关的：

| 目标 | COCO 类别 |
|---|---|
| 人员 | `person` (0) |
| 车辆 | `car` `motorcycle` `bus` `truck` `bicycle` |
| 随身物品 | `backpack` `handbag` `suitcase` |

其余类别默认过滤，但**保留可配置**——万一演示场景需要别的。

⚠️ **COCO 里没有「冒烟」「明火」「倒地」这几个类。** 异常识别必须另想办法，见 3.4。

**④ 时间同步**

RGB 与深度必须对齐。用 `message_filters.ApproximateTimeSynchronizer`（近似时间同步，因为深度与 RGB 时间戳常有微小偏差）：
- 队列深度 10
- slop 设 0.05 s 左右

#### 实现要点

- 订阅 `sensor_msgs/Image`，`cv_bridge` 转 numpy
- 预处理：`bgr8` 转换、尺寸缩放由 ultralytics 内部处理
- 输出中间结构 `Detection2D`：`class_name` / `confidence` / `bbox_xyxy` / `track_id`

### 3.2 三维定位

把像素框变成 `map` 系下的三维坐标。**两条路线，都要实现**（等盘点结果决定主用哪条）。

#### 路线 A：深度相机（首选）

```
输入: bbox + 深度图 + 相机内参 + TF(map→camera)
输出: map 系下的三维点

① 深度采样 —— 不要取单个中心像素！
   在 bbox 中心 1/3 区域内统计深度
   - 用「中位数」抗噪点
   - 更推荐「25 分位数」：检测框常含背景（人站在墙前），
     取偏前景的分位数能显著减小远偏
   - 过滤无效值：0、NaN、inf、超出量程的

② 反投影到相机系
   Z = d
   X = (u - cx) * d / fx
   Y = (v - cy) * d / fy
   （u,v 取该区域深度有效像素的对应像素坐标）

③ TF 变换到 map 系
   tf2 查 map → camera_frame（或 map→base_link 级联 base_link→camera）
   输出 geometry_msgs/Pose

④ 代表点选择 ⚠️
   bbox 中心对应的点，还是 bbox 底部中点？
   → 倒地检测推荐「底部中点」：地面接触点比身体中心更稳定，
     且倒地时身体中心会飘。
```

**坑点清单**：
- 深度图必须与 RGB **对齐**（`align_depth`），否则 u,v 对不上
- 检测框含背景 → 深度被拉远（用分位数缓解）
- 目标部分遮挡 → 深度有效像素少，需设最少有效像素阈值，不足则丢弃该检测
- 相机系定义要确认（光学系 z 向前 vs 机体系）—— 这是最容易错的地方

#### 路线 B：单目 + 地面假设（降级方案）

深度不可用时（Air 版无深度相机）的兜底：

```
已知: 相机离地高度 h、俯仰角 θ、内参
① 像素 (u,v) → 相机系射线方向
② 与地平面 z = -h 求交点
③ 变换到 map 系
```

- 只对**在地面上**的目标有效（站立/倒地的人）—— 对空中目标完全失效
- 精度显著低于路线 A，俯仰角标定误差会直接放大成距离误差
- **必须用到 G3 盘点拿到的相机安装高度与俯仰角**

#### 配置化设计

两条路线做成**同一个节点的两种策略**，通过参数切换：

```yaml
projector:
  mode: "depth"        # depth | ground_plane
  depth_quantile: 0.25 # 深度分位数
  min_valid_pixels: 10 # 最少有效深度像素
  anchor: "bottom"     # bottom | center
```

### 3.3 探索决策

**frontier 探索**：找已知区域与未知区域的边界，选收益最大的去探。

#### ① frontier 检测

输入 `nav_msgs/OccupancyGrid`（`-1`=未知, `0`=自由, `100`=占用）。

```python
# 用 OpenCV 做，比纯 Python 快几个数量级
free    = (grid == 0)
unknown = (grid == -1)

# unknown 膨胀 1 格后与 free 求交 = frontier
unknown_dilated = cv2.dilate(unknown.astype(uint8), kernel_3x3)
frontier = free & unknown_dilated

# 连通域聚类 → 若干 frontier 簇（而不是一堆散点）
n, labels = cv2.connectedComponents(frontier.astype(uint8))
```

**要点**：得到的是**簇**不是单个格子。后续每个簇出一个候选目标点。

#### ② 可通行性筛选 ⚠️ 最容易出错的一步

> 项目文档特别强调：**别把「未探索区域中间的某个点」当成目标发出去——那是墙里。**

frontier 是边界，边界本身往往紧贴墙壁，**不能直接把 frontier 格当目标点**：

```
对每个 frontier 簇：
  ① 取质心 c
  ② 从机器人位置 → c 连线方向，从 c 往回退若干格
  ③ 找第一个「free 且不在 costmap 膨胀区内」的格子作为目标
  ④ 校验：目标点周围要有足够空隙容纳 Go2 的足迹半径
     （Go2 机身较宽，膨胀层必须留够）
  ⑤ 校验失败 → 丢弃该簇
```

**不要用 `OccupancyGrid` 的原始 free 判断可通行** —— 要去查 Nav2 的 costmap，它含膨胀层。但 G2 不该依赖 G1 的内部实现……折中：G2 自己按 Go2 半径做一次 `cv2.distanceTransform`，得到「离障碍物距离图」，要求距离 > 安全半径。这样 G2 自洽，不依赖 G1 细节。

#### ③ 信息增益评分

朴素距离启发式（explore_lite 的做法）不够好，加信息增益项是 G2 的核心增量工作：

```
gain(f) = Σ_{cell ∈ window(f)} w(cell) / (dist(robot, f) + ε)^α

w(cell) = 1 if unknown else 0
window(f) = 以 frontier 簇为中心的一个窗口（半径 R 格）
dist = 沿可行路径的距离（欧氏距离会低估，绕墙时不准）
α ≈ 0.5 ~ 1.0，距离衰减指数
```

**可叠加的改进项**（按性价比排序）：

| 改进 | 作用 | 优先级 |
|---|---|---|
| **历史访问惩罚** | 防止在两个 frontier 间来回震荡 | 高 —— 不做这个必定震荡 |
| **失败黑名单** | 目标点失败/超时后临时拉黑 | 高 |
| **朝向收益** | 与当前朝向一致的优先（减少转身） | 中 |
| **语义优先** | 检出可疑目标的区域加权 | 中 —— 衔接 3.4，是加分项 |
| 路径可达性预检 | 用 costmap 判断是否真能到达 | 低（Nav2 会兜底） |

**距离用欧氏还是路径代价**：欧氏实现简单但有系统偏差（隔墙时高估收益）。建议先用欧氏，震荡问题用「历史访问惩罚」解决，比算真实路径更省事。

#### ④ 目标点状态机 ⚠️

**同一时刻只能有一个在飞的目标点**，必须有状态机管理：

```
IDLE ──选中 frontier──▶ NAVIGATING
  ▲                         │
  │                         ├─ action 成功 ──▶ IDLE（更新已探索区域）
  │                         ├─ action 失败/被拒 ──▶ 拉黑该点 ──▶ IDLE
  └──── 超时/无进展 ────────┘（拉黑并重新选）
```

- **超时判据**：目标点发出后 N 秒内，机器人到目标的距离没有明显缩短 → 判定卡住
- **黑名单有效期**：不是永久 —— 地图更新后该点可能重新变得可达，设个过期时间
- **重入保护**：收到 G3 返航指令后，立刻停止发新目标

#### ⑤ 终止条件

| 条件 | 动作 |
|---|---|
| 无可用 frontier | 探索完成，通知 G3 |
| 覆盖率 > 90%（指标要求） | 探索完成 |
| 收到 G3 返回指令 | 停止探索，不再发新目标 |
| 时间/电量上限 | 停止（电量由 G3 管，G2 只响应） |

**覆盖率自算**：已知自由格数 ÷ 可通行总面积。可通行总面积在探索开始时未知，用「当前已知自由格 + 未知格中可通行的估计」近似，或只在演示中标注已探索区域范围。这个指标和 G3 的计算口径要对齐。

#### ⑥ 为什么不直接用 explore_lite

| | explore_lite | 自写 |
|---|---|---|
| 启发式 | 距离 + 簇大小（朴素） | 信息增益 + 访问惩罚 + 语义 |
| 可定制 | 改起来要动它的插件 | 完全可控 |
| 上手速度 | 快 | 慢 |

**建议路线**：先用 `explore_lite` 把「地图 → 目标点 → 导航」的链路跑通（验证接口 02 没问题），再自写替换。别一上来就自研，会卡在链路问题上分不清是算法还是集成。

### 3.4 异常识别（第 10–14 周，加分项）

**目标**：让「侦查」从「找到人」升级到「判断异常」。零训练成本是硬约束。

#### 人员倒地检测 —— 两种方法

**方法 A：bbox 长宽比**（最简，先做）

```
正常人: bbox 高 > 宽  (h/w > 1.2)
倒地:   bbox 宽 > 高  (h/w < 0.6)
```

- ✅ 零额外模型，几行代码
- ❌ 受视角严重影响 —— **俯视时站立的人也接近方形**，会误判
- 必须结合相机俯仰角做归一化，否则换个机位就失效

**方法 B：姿态估计**（推荐）

用 ultralytics 的 pose 模型（`yolo11n-pose.pt`），COCO 17 关键点：

```
肩中点 S = (left_shoulder + right_shoulder) / 2   # 关键点 5,6
髋中点 H = (left_hip + right_hip) / 2             # 关键点 11,12
躯干向量 T = S - H

倒地判据: angle(T, 重力方向) > 60°
```

- ✅ 比长宽比鲁棒得多，不受视角影响
- ✅ 零训练成本，模型现成
- ❌ 比纯检测慢一些（可接受，抽帧后频率不高）
- ⚠️ 关键点置信度低时要丢弃（人背对、遮挡时肩髋点不可靠）

**推荐策略**：**A 快速筛选 → B 确认**。bbox 长宽比先粗筛出可疑目标，只对可疑目标跑 pose 估计，省算力。

#### 冒烟/明火检测 ⚠️ 需要明确 scope

**这是本组风险最高的子项，必须在组内先对齐预期。**

现实约束：
- COCO 无 smoke/fire 类
- 颜色/纹理启发式（HSV 阈值 + 区域增长）非常弱，光照一变就误检一堆
- 自训练一个检测器与「零训练成本」的课题前提冲突

**三个选项**：

| 选项 | 成本 | 效果 |
|---|---|---|
| ① 不做，明确从交付物中剔除 | 0 | —— |
| ② 降级为演示性功能，用 HSV 启发式，标注为「概念验证」 | 低 | 演示可以，别写进指标 |
| ③ 用开源火烟数据集（如 D-Fire）微调 YOLO nano | 中（要标数据/调参） | 能到可用水平 |

**建议走 ② 并把话说清楚**，把精力放在人员倒地（这个是能做扎实的）。如果时间有富余再考虑 ③。

#### 目标去重与跟踪

同一个人连续 10 帧被检出，**不应该发 10 条 `Detection3D`**。

- 用 ByteTrack 的 `track_id` 做主键
- 同一个 `track_id` 在时间窗内只发一次（或按固定间隔更新）
- 跨帧关联：跟踪丢失后再出现，按空间距离 + 类别关联

建议给 `Detection3D` **加一个 `uint32 id` 字段**（接口契约允许加字段）—— 没有它，G3 那边去重会很痛苦。

#### 异常输出

复用 `Detection3D`，不另开接口：
- `class_name = "person_fallen"` / `"smoke"`
- 保持与普通检测一样的字段结构，G3 无需特殊处理

## 四、接口实现

### 4.1 订阅（输入）

| 话题 | 类型 | 来源 | 用途 | 可否用假数据先行 |
|---|---|---|---|---|
| `/map` | `nav_msgs/OccupancyGrid` | G1 | frontier 探索 | ✅ 手写栅格地图 |
| `/camera/color/image_raw` | `sensor_msgs/Image` | 仿真/真机 | 检测 | ✅ 离线图片 |
| `/camera/depth/image_raw` | `sensor_msgs/Image` | 仿真/真机 | 深度 | ✅ 生成合成深度图 |
| `/camera/color/camera_info` | `sensor_msgs/CameraInfo` | 相机 | 内参 | ✅ 手填 |
| TF `map → camera` | `tf2` | G1 | 坐标变换 | ✅ 发静态 TF |
| `/cloud_map`（可选） | `sensor_msgs/PointCloud2` | G1 | 障碍判断 | —— |

**注意**：话题名以 G1 实际发布的为准，先按上表写，联调时对齐。**这是联调第一个要确认的东西。**

### 4.2 发布（输出）

| 话题/action | 类型 | 目标 | 内容 |
|---|---|---|---|
| `/navigate_to_pose` | `nav2_msgs/action/NavigateToPose` | G1 | 探索目标点 |
| `/detections_3d` | `vision_interfaces/msg/Detection3D` | G3 | 目标消息 |
| `/exploration_status` | 自定义 | G3 | 状态（IDLE/NAVIGATING/完成）可选 |

### 4.3 `Detection3D` 消息定义（接口 03）

第一周就冻结，越早越好：

```
# vision_interfaces/msg/Detection3D.msg
string                    class_name    # 类别（含 person_fallen / smoke 等异常类）
float32                   confidence    # 置信度 0~1
geometry_msgs/Pose        pose          # 三维坐标，map 系
builtin_interfaces/Time   stamp         # 时间戳（图像采集时刻，不是处理时刻）
sensor_msgs/Image         snapshot      # 抓拍图
uint32                    id            # 跟踪 ID，用于去重   ← 建议新增
```

**两点说明**：

- **`id` 是建议新增的字段**。契约允许「加字段」，不加的话 G3 无法区分「同一个人的连续上报」和「两个不同的人」。请在全队提出来。
- **`snapshot` 会让消息很重**。每次检测都带一张图，rosbag 会迅速膨胀。建议加一个参数 `publish_snapshot`，默认开启（演示需要），跑长时实验时关掉。

**语义冻结的红线**：`pose` 是 **map 系**。改坐标系（比如改成相机系）必须全队通知 —— 这是文档里点名的例子。

## 六、里程碑与排期

项目总排期里 G2 是「6–10 周检测与三维定位、8–12 周探索策略、10–14 周异常识别」。但文档也说了 **G2 不用等 G1**，所以实际可以大幅提前：

| 周次 | 感知链路 | 探索链路 | 交付 |
|---|---|---|---|
| **1** | `Detection3D` 消息定义冻结合进 develop | 熟悉 explore_lite 源码 | **接口 03 冻结** |
| 2–4 | ultralytics 跑通离线图片/视频；假 TF 跑通像素→三维 | 手写假栅格地图，实现 frontier 检测 + 可通行校验 | 两条链路各自跑通 |
| 5 | RGB-深度同步、抽帧、跟踪 | 信息增益 + 访问惩罚 | |
| 6–10 | **接 G1 真数据**，检测+三维定位联调 | explore_lite 接真地图跑通接口 02 | 感知链路交付 |
| 8–12 | 精调（遮挡、远距离、误检） | 自写探索替换 explore_lite | **探索策略交付** |
| 10–14 | 异常识别（pose 倒地 + 冒烟降级） | 语义优先探索（结合检测结果） | **异常识别交付** |
| 13–16 | 配合 G3 评测，保证检出率/误检率达标 | 配合覆盖率指标 | 指标报告支撑 |

**关键前置动作（第 1 周必做）**：

2. 找 G3 要设备盘点结果中与视觉相关的三项：**有无深度相机 / 相机内外参 / 机载算力**

**第 6 周关卡**：项目文档定的第一个里程碑是「真机遥控建图跑通」。对 G2 而言对应的是**检测链路能在真机数据上出结果**。如果那时设备盘点还没结论，视觉方案要立刻按「无深度相机」的降级路线重排。

## 七、风险与对策

| 等级 | 风险 | 影响 | 对策 |
|---|---|---|---|
| **高** | 无深度相机（Air 版） | 三维定位降级，精度大跌 | 路线 B 提前实现；等 G3 盘点，越早越好 |
| **高** | COCO 无火/烟类 | 冒烟检测做不了 | **明确 scope 降级为演示**，别写进指标 |
| 中 | 机载算力不足 | YOLO 跑不到实时 | nano + ONNX/TensorRT + 抽帧；离线回传兜底 |
| 中 | 检测框含背景 | 三维坐标系统性偏远 | 深度取分位数不用均值 |
| 中 | G1 地图质量差 | frontier 检测不稳 | 假地图先开发；加地图质量检查（未知率突变告警） |
| 中 | frontier 目标点在墙里 | 导航反复失败 | 可通行性校验（3.3②）；这是文档点名强调的坑 |
| 中 | 目标点来回震荡 | 覆盖率上不去 | 历史访问惩罚 + 失败黑名单（必做） |
| 低 | TF 未就绪 | 三维定位阻塞 | 假 TF 先跑通 |
| 低 | 时间戳不对齐 | 检测结果错配 | 用图像采集时刻，不是处理完成时刻 |

## 八、测试策略

| 层级 | 内容 | 何时 |
|---|---|---|
| **单元测试** | frontier 检测：构造已知栅格地图，断言 frontier 位置；三维投影：给定内外参，手算验证数值；增益评分：构造场景验证排序 | 第 2–4 周 |
| **离线测试** | COCO 图片/视频跑检测，人工核对检出率 | 第 2 周起 |
| **回放测试** | rosbag 回放，可重复验证 | 第 6 周起 |
| **仿真联调** | 接 G1 真地图 + 真 TF | 第 6 周起 |
| **指标验证** | 检出率 > 85%、误检率 < 10% | 第 13 周起 |

**三维投影的验证方法**：在仿真里放一个已知 `map` 系坐标的目标（比如把一个人模型放在 (5, 3)），跑完整链路，看输出的 `pose` 和真值差多少。**这个测试必须在接真机之前做**，否则上真机后分不清是投影错了还是标定错了。

**记 rosbag 的习惯**：每次实验自动落盘（接口 04 的要求）。G2 尤其需要 —— 检测效果的问题往往要回放才能定位。

## 十、一句话总结

**G2 的两条链路互相独立、且都不依赖 G1 的完成 —— 这是本组最大的进度优势。**

感知链路（检测 → 三维）和探索链路（地图 → 目标点）可以并行走，各自用假数据跑通，等 G1/G3 的真数据到位再对接。

**优先级排序**：接口 03 冻结 > 检测跑通 > 三维定位 > frontier 探索 > 异常识别。

**唯一要先说清楚 scope 的**：冒烟检测在没有训练数据的前提下难以做好，建议明确降级为演示性功能，把精力集中在能做扎实的人员倒地识别上。
