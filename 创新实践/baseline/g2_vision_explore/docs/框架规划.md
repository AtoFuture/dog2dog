## 一、职责边界

**一句话：只决定「去哪」，不碰「怎么走」。**

```
        G2（决策层）                      G1（执行层）
  frontier / 信息增益  ──发目标点──▶   Nav2 路径规划
  「下一片没探过的区域」               代价地图 / 绕障 / TF / 路径
```

| G2 负责 | G2 **不碰** |
|---|---|
| 目标检测、三维坐标解算 | 路径规划、代价地图配置 |
| 选下一个探索目标点（位置 + 朝向） | `map → odom → base_link` 的发布 |
| 异常识别 | 避障、恢复行为 |
| 发布 `Detection3D` | 底盘控制、DDS 通信 |

### 关于「不等 G1」的准确表述

v1 写的是「G2 可以完全不等 G1」，**这个说法过头了**，会造成误解。准确的是：

> **接口上独立、开发期可并行、但指标上耦合。**

- **开发期确实可以并行**：假地图 + 假 TF + 假 action server 就能把两条链路的逻辑全部跑通
- **但运行期有三处硬耦合**：① 联调时间点两条链都要接 G1；② 覆盖率指标同时取决于 G1 的建图质量和 G2 的探索策略；③ 语义优先探索要吃检测结果（见 4.3）
- **结论**：可以提前开工，但**不能假设 G1 的接口会按时可用** —— 具体日期要去要（见第十一节）

## 二、运行环境前提 ⚠️ 本节是 v1 的最大遗漏

以下三条不解决，代码写得再对也跑不起来，而且**报错信息会指向别处**，极难自查。

### 2.1 仿真时间基准（`use_sim_time`）

**gz-sim 下所有节点必须统一设 `use_sim_time: true`。**

- ROS2 里 `use_sim_time` 是**逐节点参数**，不是全局开关。必须通过 launch 给**每一个节点**设：
  ```python
  Node(..., parameters=[{'use_sim_time': True}])
  ```
- `/clock` 由 `ros_gz_bridge` 桥接，**必须是单向 gz→ros**（bridge 参数里 `[` 和 `@` 用错会建不出桥）
- 后果：不设的话节点用墙钟、`/clock` 是仿真钟，TF 报 `extrapolation into the past/future`。
  **v1 把「TF 查不到」列为低风险，是误判** —— 这会是仿真联调第一个卡住的地方
- 回放 rosbag 时同样要设，且必须 `ros2 bag play --clock`

**G2 需要设的节点**：检测节点、投影节点、探索节点、任何查 TF 的节点。

### 2.2 QoS 兼容性 —— 「一帧都收不到」的元凶

rclpy 订阅默认是 **RELIABLE**，而相机/雷达话题几乎都是 **BEST_EFFORT**（`qos_profile_sensor_data`）。

**QoS 不兼容时不报错、不抛异常**，只在启动时打一行 `incompatible QoS ... RELIABILITY` 警告，然后**一帧都收不到**。这是 ROS2 视觉节点最常见的第一号坑。

```python
from rclpy.qos import qos_profile_sensor_data
# 图像、点云订阅一律显式指定
self.create_subscription(Image, topic, cb, qos_profile_sensor_data)
```

**要求**（写进接口契约，第一周冻结）：

| 话题 | QoS 约定 |
|---|---|
| 图像 / 深度 / 点云 | `BEST_EFFORT` + `VOLATILE` + `KEEP_LAST(1~5)` |
| `/map` | durability 与 G1 约定（建议 `TRANSIENT_LOCAL`，否则 G2 晚启动就拿不到已有地图） |

**联调第一件事**：`ros2 topic info /topic --verbose` 看实际的 QoS，别猜。

### 2.3 时钟一致性

`message_filters` 近似同步、tf2 按 stamp 查询、rosbag 回放、覆盖率-时间曲线 —— 全部依赖统一时钟。上面 2.1 解决仿真，回放时用 `--clock`。

## 四、模块分解

### 4.1 目标检测

**选型：`ultralytics` + COCO 预训练权重，零训练成本。**

#### ① 模型代际 —— v1 落后了一代半

v1 写 `yolo11*.pt` 配「ultralytics 最新版」，这等于**用最新框架跑两代前的模型**。

现状（截至 2026-09）：

| 家族 | 状态 | COCO mAP(50-95) n/s/m/l |
|---|---|---|
| YOLO11 | 仍受支持，但**不是当前推荐家族** | 39.5 / 47.0 / 51.5 / 53.4 |
| **YOLO26** | 自 `ultralytics 8.4.0` 起发布，官方定位 **recommended latest stable** | **40.9 / 48.6 / 53.1 / 55.0** |

YOLO26 同尺寸全面更高，且 **CPU 推理快 43%** —— 后者正好命中「机载算力不足」和「回传后处理」两条降级路线。

> ⚠️ **一个必须说明的矛盾**：ultralytics 官方的 **YOLO11 页面至今仍写着 "Current stable release and the recommended choice for all use cases"**，与 YOLO26 页面的定位互相打架。这是官方文档自己没更新。
> 所以准确的结论是「**yolo11 落后一代半**」，不是「不能用」。**稳妥做法：两代都验，按实测 mAP/延迟定**（见第十节待决项）。

模型分档（等设备盘点定）：

| 场景 | 建议 | 说明 |
|---|---|---|
| 开发 / 验证 | `yolo26l.pt` | 先确认效果上限，不纠结速度 |
| 仿真 | `yolo26m.pt` | 仿真机通常有显卡 |
| 真机（有 Orin） | `yolo26s.pt` | **TensorRT engine 必须在 Orin 上导出** —— 与 GPU 架构强绑定，x86 上生成的拷过去不能用 |
| 回传处理 | `yolo26m/l.pt` | **注意**：v1 在这里写了 nano，是逻辑矛盾 —— 既然回传到 4090 处理，就不该用端侧的小模型 |

**顺序**：先按最大的跑确认上限，再逐步往下砍。反过来做会分不清「检测器不行」还是「模型太小」。

#### ② 抽帧 + 跟踪

相机不需要 30 Hz 推理，抽帧到 **5 Hz** + 跟踪复用轨迹。

> ⚠️ **关于帧率的修正**：v1 写「相机 30 Hz」。**Go2 原生前视相机是 15 fps 档**（720p/1080p @15fps），30 Hz 只在加装 D435i 时成立。抽帧比例按实际帧率算。

**跟踪器选型 —— v1 的 ByteTrack 选错了**：

- ultralytics 现内置 **6 个** tracker，`cfg/default.yaml` 的默认值是 **`tracktrack.yaml`**，**不是 ByteTrack**
- 官方对 ByteTrack 的定位是「最快最简的基线，**适合静态或近似静态相机**」
- **Go2 是四足运动平台** —— 机身起伏 + 转向，帧间位移的主因是**相机自身运动**。ByteTrack 没有相机运动补偿（GMC）也没有表观特征，**ID switch 会很多**
- 而去重和跨帧关联（见 4.4）**都依赖 `track_id` 稳定**

```python
# 用带 GMC 的 BoTSORT，或当前默认的 tracktrack
model.track(frame, persist=True, tracker="botsort.yaml")
```

第一周用实测 ID-switch 率选型，别写死。

**输出频率要写死**：中间帧的跟踪结果**只用于可视化，不入消息**。建议 `Detection3D` 的输出频率 = 推理频率（5 Hz）。v1 的「中间帧用跟踪结果补齐」没说清是发 5 Hz 还是插值到 30 Hz —— 后者叠加 0.92 MB/条的消息（见 5.3）意味着 27 MB/s。

#### ③ 类别关注范围（已核实）

COCO 80 类里与侦查相关的：`person`(0) · `car`(2) · `motorcycle`(3) · `bus`(5) · `truck`(7) · `bicycle`(1) · `backpack`(24) · `handbag`(26) · `suitcase`(28)。

⚠️ **COCO 里没有「冒烟」「明火」「倒地」这几个类**，异常识别必须另想办法（见 4.4）。

#### ④ 时间同步

RGB 与深度用 `message_filters.ApproximateTimeSynchronizer`。

- **只同步 `Image + Image` 两路**。`CameraInfo` 是准静态的，用 `TRANSIENT_LOCAL` 订阅一次即可 —— 放进同步器只会降低配对成功率
- **TF 查询一律用彩色图的 stamp**（内参和深度都对齐到彩色）
- **slop 要有误差预算**（v1 的 0.05 s 是拍的）：Go2 行走约 1 m/s、转向 0.5–1 rad/s 时，**50 ms 同步误差 = 5 cm 位置 / 1.5–3° 姿态**，这个误差直接进 map 系坐标

#### ⑤ 实现注意

YOLO 推理是**同步阻塞**的 Python 调用。用默认单线程 executor 的话，推理期间同节点的 TF 订阅、参数回调全部饿死；TF 的 `lookup_transform(..., timeout)` 在图像回调里阻塞还会占住线程。

→ 用 `MultiThreadedExecutor` + `MutuallyExclusiveCallbackGroup` / `ReentrantCallbackGroup` 做回调分组。

#### ⑥ 目标去重（v1 放错了节）

v1 把去重放在 4.4（异常识别），**不对** —— 它直接决定检出率/误检率的数值，属于检测的职责：

- 同一个 `track_id` 在生命周期内**只发一次**（或按固定间隔更新）
- 跨帧关联窗口、更新间隔**必须写进接口 03 的口径说明**（第一周冻结）
- **指标统计基于去重后的消息** —— 同一个场景，去重策略换一下，指标能差一个量级

### 4.2 三维定位

把像素框变成 `map` 系下的三维坐标。**三条路线**（v1 漏了第三条）。

#### 路线 A：深度相机

```
① 深度采样 —— 不要取单个中心像素！
   ⚠️ v1 写「取区域内 25 分位深度」，有两个问题：
      (a) 分位数不是标准做法，且有反向偏差：框内有更近的前景
          （桌椅、遮挡物）且占比 ≥25% 时，会偏到前景上，距离判「过近」
      (b) 更严重：分位深度来自 A 像素，而坐标却用 bbox 中心 —— 两者
          不是同一个点。fx≈600、d=5m、偏差 40px 时横向差 0.3–0.5m

   正确做法（按优先级）：
     1. 用分割掩膜限定像素：yolo26*-seg.pt 是 COCO 预训练、零训练成本，
        掩膜内采样严格优于 bbox 内的分位数启发式，且对遮挡更鲁棒
     2. 退而求其次：把区域内【所有有效像素整体反投影】，
        对 X/Y/Z【分别取中位数】，并用 X/Y/Z 的离散度做质量门限
     3. 若用分位数，必须标为「需实测标定的超参」，并让 (u,v) 与 d 同源

② 反投影到相机系（公式本身正确，ROS 光学系 z前/x右/y下）
   Z = d ;  X = (u-cx)*d/fx ;  Y = (v-cy)*d/fy

③ TF 变换到 map 系

④ 代表点：center = 目标三维质心 / bottom = 3D 包围盒底面中心
   ⚠️ 不能用「框内的分位数深度」实现 bottom —— 框底中点的深度是脚前的
      地面，与躯干深度不是同一个点
```

**坑点清单**：

| 坑 | 说明 |
|---|---|
| **深度编码** | `16UC1`（**毫米**，0=无效）vs `32FC1`（**米**，NaN=无效）。**搞错差 1000 倍**，且症状像「深度全是无效值」，会被误诊为相机故障。必须按 `msg.encoding` 分支，并写单元测试（两种编码构造假图，断言输出一致） |
| **畸变** | Go2 头部相机 **120° 广角**，理想针孔模型在边缘不可忽略。输入必须是**去畸变后**的图像，且要写清 G2 拿到的是 raw 还是 rectified |
| 对齐 | 深度必须与 RGB 对齐（`align_depth:=true`），否则 u,v 对不上 |
| 相机系定义 | 光学系（z向前）vs 机体系 —— 最容易错的地方 |
| 无效值 | 除 0/NaN/inf 外还要过滤超量程 |
| 遮挡 | 有效像素不足时丢弃该检测 |

#### 路线 B：单目 + 地面假设（降级方案）

> ⚠️ **v1 严重低估了它的限制**。v1 只说「精度显著低于路线 A」，听起来像「差一点」。
> 实际上有**硬性距离上限**：地面距离 = `h / tan(θ + φ)`，图像中心对应**最远可视距离 = h/tanθ**。

按 Go2 站立约 40 cm、相机在头部取 `h≈0.35 m`：

| 下俯角 θ | 有效距离上限 |
|---|---|
| 10° | 约 **2.0 m** |
| 5° | 约 **4.0 m** |
| 3° | 约 6.7 m，但可用像素挤在地平线附近，角分辨率急剧恶化 |

**结论：路线 B 的可用距离很可能只有几米，只能覆盖近场。** 侦查场景是要看远方的 —— 这决定了它在「无深度相机」时到底还值不值得做。

其它要求：
- **外参来源改用 URDF/TF 的完整外参**，不要只标定 `h` 和 `θ` 两个标量（map 系坐标还需要相机相对 base_link 的横向/纵向偏移与偏航，否则整幅点云整体平移+旋转）
- 必须加「**射线朝上（地平线以上）→ 判废**」检查，否则会产生反方向/无穷远的假坐标

#### 路线 C：点云簇关联（v1 完全漏掉）

接口 01 里 `PointCloud2` 是 G1 的**正式输出**，v1 却把它标成「可选/障碍判断」。

如果盘点下来**有激光雷达**（Pro/Edu），「2D 框 → 点云簇质心」是移动机器人目标三维定位的**标准做法** —— 比单目地面假设鲁棒得多，且不依赖深度相机。

**投影器配置化，三条路线统一入口**：

```yaml
projector:
  mode: "depth"          # depth | ground_plane | lidar_cluster
  depth_quantile: 0.25   # 仅 depth 模式，需实测标定
  min_valid_pixels: 10
  anchor: "center"       # center | bottom
  max_dispersion: 0.5    # X/Y/Z 离散度门限
```

### 4.3 探索决策

#### ① frontier 检测

```python
import numpy as np, cv2
free    = (grid == 0)
unknown = (grid == -1)

# unknown 膨胀 1 格后与 free 求交 = frontier
dil = cv2.dilate(unknown.astype(np.uint8), np.ones((3,3), np.uint8))
frontier = (free & (dil > 0)).astype(np.uint8)

n, labels = cv2.connectedComponents(frontier)

# ⚠️ v1 漏了：最小簇过滤。栅格噪声会产出单格小簇，
#    每个都被当候选目标点 → 白跑一趟。explore_lite 的
#    min_frontier_size 默认 0.5 m，必须照做
```

> ⚠️ **取值域冲突（v1 内部矛盾）**：`-1/0/100` 是 `nav_msgs/OccupancyGrid` 的规范约定，① 里用它合法；
> 但 **Nav2 costmap 内部是 `0–255`**（`NO_INFORMATION=255`、`LETHAL=254`、`FREE=0`）。
> 若真去订阅 costmap，`grid == -1` 永远不成立，判定全失效。
> **契约写死：G2 只消费 `/map`（`-1/0/100`），不消费 costmap。**
> 第一周用 `ros2 topic echo` 实测 G1 的 `/map` 取值域（RTAB-Map 输出是否符合规范要实盘确认）。

#### ② 可通行性筛选 —— v1 的算法是错的

> v1 写「从机器人位置 → 质心连线方向，从 c 往回退若干格」。
> **这是错的**：当 frontier 在**墙的另一侧**（透过门洞看到的未知区）时，机器人→质心的直线**穿墙**，
> 「往回退找到的第一个 free 格」仍在墙那边，照样不可达。
> v1 自己在 ③ 里写了「欧氏距离绕墙时不准」，却在选点上用了直线回退 —— 同一份文档自相矛盾。

**正确做法**：在 free 空间上从机器人位姿做 **BFS/Dijkstra 测地展开**，每个 frontier 簇取「到机器人**测地距离最小**的那个 free 格」作为目标点。

explore_lite 就是这么做的 —— 直接复用其做法即可，不需要自研。

**关于安全半径（v1 的「自洽」结论是错的）**：

> v1 写「G2 自己按 Go2 半径做 distanceTransform 就自洽，不依赖 G1 细节」。
> **危险**：若 G2 的安全半径 < G1 Nav2 的 `inflation_radius` / `robot_radius`，
> G2 会把点选在 Nav2 判定为内切/致命代价的格上 → Nav2 拒绝或触发恢复行为 →
> G2 超时拉黑 → 换点 → 覆盖率上不去，而**现象上会表现为「G1 导航不行」**，跨组扯皮。

**要求**：Go2 的 footprint 半径、G1 的 `inflation_radius`、G2 的安全半径**写进接口契约作为冻结参数，三者同源**。G2 自算距离图仅作快速预筛，不作最终判据。

`cv2.distanceTransform` 的三个约定（v1 一个都没写）：
1. 传参必须是 `1 - occupied`（语义是「到最近**0**像素的距离」，写反结果正好相反）
2. 结果单位是**格**，要乘 map resolution 才是米
3. 默认 `DIST_L2` + 3×3 掩膜是**近似**欧氏距离，要精确得用 `DIST_MASK_PRECISE`

#### ③ 信息增益评分 —— 核心增量可能不成立

```python
# v1 的公式（有问题）
gain(f) = Σ_{cell ∈ window(f)} w(cell) / (dist(robot, f) + ε)^α
```

**两个问题**：

1. **α 没有依据**：文献更常见的是**指数衰减 `e^(−λd)`**（λ 有明确 1/m 量纲）；`α=1` 对应经典「收益/代价」；**`α=0.5` 找不到出处**。把幂律叫「距离衰减指数」是把两种函数族混为一谈。

2. **更实质的：公式会退化**。`w=1` 只数「窗口内的未知格」，而窗口以 frontier 簇为中心 —— 对任何「外侧是一片未知」的 frontier，这个和都会**饱和到 ≈ 窗口面积**，于是排序几乎完全由 `1/dist^α` 决定 → **退化成「最近的 frontier」，也就是 v1 自己批评的 explore_lite 行为**。而且窗口里「墙后面的未知格」也被计入，实际观测不到。

**改法**：
- 距离折扣改用 `e^(−λd)`，给出选 λ 的方法（如「2 m 与 10 m 处收益权重比为 X」）
- `w` 改为**从候选视点可观测到的未知格数**（沿视点做一次射线可见性判定），或至少除以窗口面积归一化

**可叠加的改进项**（按性价比）：

| 改进 | 作用 | 优先级 |
|---|---|---|
| **历史访问惩罚** | 防止在两个 frontier 间来回震荡 | **高 —— 不做必定震荡** |
| **失败黑名单** | 目标点失败/超时后临时拉黑 | 高 |
| **目标朝向** | 见 ④，决定抵达后能不能看到未知区 | **高（v1 遗漏）** |
| 语义优先 | 检出可疑目标的区域加权 | 中 —— 衔接 4.4，是加分项 |
| 路径可达性预检 | 用 costmap 判断是否真能到达 | 低（Nav2 会兜底） |

**关于 explore_lite，v1 的描述是错的**：

> v1 写它「用的是朴素距离启发式」「距离 + 簇大小（朴素）」，并据此说「加信息增益项就是你们的增量」。
> **核实结果**：m-explore-ros2 的 `frontierCost` 是
> `potential_scale * min_distance * resolution − gain_scale * size * resolution` ——
> **已经同时包含距离项和簇大小项**。而且它的 `min_distance` 是**测地（BFS）距离**，
> 比 v1 建议的欧氏距离**还更准**。
> v1 因此**低估了 explore_lite，也高估了自己的增量**。工作量估计要据此调整。

#### ④ 目标点的朝向 —— v1 从头到尾没设 ⚠️

`NavigateToPose` 的 goal 是 `PoseStamped`，**`orientation` 是「最终抵达的朝向」**。v1 只选位置，从没提 yaw。

**对「视觉探索」课题这是致命的**：狗抵达 frontier 后朝哪边，直接决定它能不能看到那片未知区域。**朝墙的话这一趟白跑**，而且这个错误**不会报任何错**，只表现为「探索很慢 / 覆盖率上不去」。

```python
# 目标朝向 = 从目标点指向【附近那片】frontier 的方位角
yaw = atan2(cy - ty, cx - tx)   # (cx, cy) 必须是局部质心，不是整簇质心
```

> ⚠️ **不能用整簇质心**（实现阶段发现）。矩形房间的 frontier 是一个**闭环**，
> 它的质心恰好是**房间正中心** —— 据此算出的朝向会指向房间内部，
> 狗走到边界后**面朝房间**，这一趟白跑，而且不会有任何报错。
>
> 正确做法：取目标点附近（约 1.5 m 内）的 frontier 格，**按距离加权**求质心。
> 权重不能省 —— 在房间**角落**附近，窗口截到的是一段 L 形边界，
> 简单平均会把 L 的另一条边也拉进来，质心又落回房间内部。
>
> 同样的原因，**黑名单和访问惩罚也必须比对候选点本身，不能比对簇质心** ——
> 比对质心在闭环 frontier 下等于永远不生效。

> v1 的改进项里只有「朝向收益：与当前朝向一致的优先（**减少转身**）」—— 方向正好相反，
> 那是省时间，这是决定**看到什么**。

#### ⑤ 状态机 —— 缺「被抢占」分支

```
IDLE ──选中 frontier──▶ NAVIGATING
  ▲                         │
  │                         ├─ SUCCEEDED ──────▶ IDLE（更新已探索区域）
  │                         ├─ ABORTED/REJECTED ─▶ 拉黑该点 ─▶ IDLE
  │                         ├─ 超时/无进展 ──────▶ 拉黑并重选
  └─────────────────────────┤
                            └─ ⚠️ 被抢占（非自己发起的 cancel/abort）
                                  ──▶ PASSIVE：不重发目标，等待恢复
```

**为什么必须有「被抢占」分支**：低电量返航走的是**同一个 action server**（契约明写「复用这条通路，不另开接口」）。G3 的返航点会**抢占 G2 在飞的目标**。v1 的状态机没有这个分支，G2 会继续选下一个 frontier 再抢占回来，**两边打架**，直接威胁项目指标「返航成功率 100%」。

> **契约空白**：v1 写「收到 G3 返航指令后停止发新目标」—— 但**契约里根本没有 G3→G2 这条接口**。
> 这是 v1 虚构的信号。**最小方案**见第十节待决项。

其它要素：
- **超时判据**：目标点发出后 N 秒内，到目标的距离没有明显缩短 → 判定卡住
- **黑名单**：给具体默认值（如 **30 s 过期**），不要只说「设个过期时间」
- **地图更新导致目标点失效**：选定 frontier 后走到之前，G1 可能已经把它探掉了 —— **中途要校验**
- **Action client 要素**：goal handle、feedback 回调、cancel 时机、`result` 状态码（`SUCCEEDED`/`ABORTED`/`CANCELED`）

#### ⑥ 终止条件

| 条件 | 动作 |
|---|---|
| 无可用 frontier | 探索完成 |
| 覆盖率达标 | 探索完成（口径见第十节） |
| 收到返航信号（**接口待立**） | 转 PASSIVE |
| 时间/电量上限 | 停止 |

**覆盖率自算**：v1 写的「已知自由格 ÷ (已知自由格 + 未知可达格的**估计**)」是**自证式指标** —— 估计乐观就提前停、漏检目标；保守就永不终止。而 v1 还把它写成了**终止条件**。

→ 见第十节：**报告数字一律用真值口径，实时自算只用于监控和辅助判据**。

### 4.4 异常识别

**目标**：让「侦查」从「找到人」升级到「判断异常」。零训练成本是硬约束。

#### ⚠️ 首先：预训练检测器在躺姿上召回本身就存疑

**这是 v1 完全没意识到的前提风险。** 下面方法 A 和方法 B **都建立在「COCO 预训练 YOLO 能稳定检出躺姿的人」之上**。

已有文献指出：COCO 缺少躺姿样本，YOLO 会把蹲/躺的人预测成 `dog`，且这些检测错误是端到端倒地检测误报的**主要来源**。「零训练成本」这条路线在这里恰恰是最脆弱的一环。

**对策（零成本、必须提前做）**：**第 2–4 周**就用真实躺姿图片（自己躺地上拍几十张）**实测 recall**，而不是等第 10 周。结论决定要不要走「少量数据微调」（与课题前提冲突，需要早提）。

#### 人员倒地检测

**方法 A：bbox 长宽比**（快速粗筛）
```
站立: h/w > 1.2 ；倒地: h/w < 0.6
```
受视角严重影响（俯视时站立的人也接近方形），**必须结合相机俯仰角归一化**。

**方法 B：姿态估计 + 3D 重力对齐**（确认）

用 `yolo26n-pose.pt`，COCO 17 关键点（索引已核实：5/6=肩、11/12=髋）。

> 🔴 **v1 的判据是反的，照抄会把站着的全判成倒地**
>
> v1 写：`T = S − H`（肩中点 − 髋中点），判据 `angle(T, 重力方向) > 60°`。
> **站立时肩在髋上方，T 朝上；重力朝下，两者夹角 = 180°，满足 `> 60°`** —— 完全反了。
>
> 🔴 **而且用 2D 关键点本身就做不到「不受视角影响」**（v1 写的「比长宽比鲁棒得多，不受视角影响」是过度承诺）：
> `keypoints.xy` 是**像素坐标**。从 2D 图像平面算出的躯干方向，只有在相机光轴水平且无 roll 时才接近「与重力的夹角」。
> ① Go2 头部相机几乎必然下俯 → 站立的人躯干在图像里也不再竖直；
> ② **沿光轴躺倒的人（脚朝相机）在图像里几乎是竖直的，会被判成站立** —— 这是**方向性漏检**，
> 不是精度问题。

**正确做法**：**肩/髋关键点用深度反投影到 3D，在 map（重力对齐）系里算夹角。**
§4.2 的深度链路**已经具备这个能力** —— 两条链路应该**合并**，而不是像 v1 那样并列成两节。

```python
S3 = backproject(shoulder_kpts_2d, depth, K, T_map_camera)
H3 = backproject(hip_kpts_2d,      depth, K, T_map_camera)
T  = S3 - H3
fallen = angle_between(T, np.array([0,0,1])) > 60 * pi/180   # 与【竖直向上】比
# 单元测试必须包含「站立」「倒地」两个人工向量 case
```

**推荐策略**：A 快速粗筛 → B（3D）确认。关键点置信度低时丢弃。

#### 冒烟/明火检测 —— 需要全队拍板，不是组内能定的

现实约束：COCO 无 smoke/fire 类；颜色/纹理启发式光照一变就误检；自训练与「零训练成本」冲突。

> ⚠️ **v1 的处理方式不对**：
> ① `baseline/g2_vision_explore/README.md` 交付物 3 的验收标准**白纸黑字**写着
> 「人员倒地、**设备冒烟**等在演示场景里能报出来」—— 这是**项目文档体系里的验收条件**。
> v1 只说「组内对齐预期」，**没有提出修改验收标准**，等于交付时大概率被判不合格。
> ② v1 说「别写进指标」也**没有落地机制** —— smoke 走 `Detection3D`，G3 按
> 「错误检出数 ÷ **全部检出数**」算误检率时，HSV 的误检会被算进去。要排除就得**改项目级指标定义**，那是全队级的决定。
> ③ **决定时点太晚**：v1 拖到 10–14 周才处理，而项目文档反复强调「越早盘越好、立刻通知全队」。
> ④ **成本算错了**：项目选题的第一理由就是「几乎不占卡」，**一个 nano 的 D-Fire 微调是数小时级**，
> 成本远小于「演示时冒烟报不出来」的交付风险。**不建议在没试过的情况下直接降级。**

→ 见第十节，列为需全队拍板项。

#### 异常输出的字段语义 —— v1 说「G3 无需特殊处理」是错的

> 🔴 v1 写「复用 `Detection3D`，`class_name = "person_fallen" / "smoke"`，**G3 无需特殊处理**」。
> 但按 `baseline/README.md` 硬规矩 2，把 `class_name` 的取值域从 COCO 类扩张，
> 且让 `confidence` 的含义从「检测器置信度」变成「启发式分数」—— **这属于「改语义」，必须全队通知**，不是「只加字段」。
> 更糟的是时点：异常识别排在第 10–14 周，**正是 G3 的系统集成期**。

**改法**：用**加字段**代替改语义。

```
string source        # coco | pose | heuristic    ← G3 可确定性过滤，不靠字符串约定
bool   is_anomaly    # 或独立布尔位
```

> ⚠️ **v1 的话题名有错，且背后有一个更大的未核实假设。**

| 话题 | 类型 | 来源 | 用途 |
|---|---|---|---|
| `/map` | `nav_msgs/OccupancyGrid` | G1 | frontier 探索 |
| 图像 / 深度 | **待盘点确认** | 相机 | 检测 |
| `CameraInfo` | **可能不存在** | 相机 | 内参 |

| TF `base_link → camera` | `tf2` | **待定（见下）** | 坐标变换 |
| `/cloud_map` | `sensor_msgs/PointCloud2` | G1 | **路线 C 三维定位**（v1 标成"可选"是错的） |

**修正 1 —— 深度话题名**：v1 写的 `/camera/depth/image_raw` **不存在**。RealSense 驱动实际是：
- `/camera/depth/image_rect_raw`

### 5.3 `Detection3D` 消息定义（接口 03）

```
# vision_interfaces/msg/Detection3D.msg
string                    class_name    # 类别
float32                   confidence    # 置信度 0~1
geometry_msgs/Point       point         # 三维坐标，map 系   ← 见下
builtin_interfaces/Time   stamp         # 图像采集时刻（非处理时刻）
sensor_msgs/CompressedImage snapshot    # 抓拍图，ROI 裁剪 + JPEG  ← 见下
uint32                    id            # 跟踪 ID，用于去重
string                    source        # coco | pose | heuristic
```

**三个相对 v1 的改动：**

**① `geometry_msgs/Pose` → `Point`**（或 `PoseWithCovariance`）
v1 用 `Pose` 但没定义 `orientation` 的含义 —— 下游会各自解释，可能有人当目标朝向用。检测结果只有一个点，用 `Point` 更诚实；要表达不确定度就用 `PoseWithCovariance`（4.2 的深度采样本来就能算出离散度）。

**② `sensor_msgs/Image` → `sensor_msgs/CompressedImage`（ROI 裁剪 + JPEG）**
v1 把它当成 rosbag 体积问题，**低估了传输层**：640×480 rgb8 ≈ **0.92 MB/条**；RTPS 默认 UDP 报文约 64 KB，大消息必须分片，**丢一片就要重传整个 sample**；ROS2 社区公认 **≥1 MB 的消息开始出问题**，Fast DDS 在 shared memory + BEST_EFFORT 下 **>0.5 MB 就有偶发丢包报告**。

按 v1 的设计（5 Hz × N 个目标，每条带整图），`/detections_3d` 会成为链路上最重的话题，跨机回传时更糟。

**改法（建议 a+b 组合）**：
- a. 只发**裁剪后的目标 ROI** + JPEG，典型 20–50 KB/条，**两个数量级的差别**
- b. 图放**独立话题**，用 `id` + `stamp` 做外键 —— G3 只要轻量消息就能去重/统计，抓拍图按需订阅

**③ 新增 `source`**（见 4.4 末）

**补充（v1 缺失）**：嵌套消息后 `CMakeLists.txt` 必须写
```cmake
rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/Detection3D.msg"
  DEPENDENCIES sensor_msgs geometry_msgs builtin_interfaces)
```
且 `package.xml` 要有对应 `<depend>`。**不写第一周就编译失败，且报错不直观。**

**还没冻结的（比坐标系更容易被悄悄改）**：`class_name` 的取值域（除异常类外还有哪些？大小写？）、`confidence` 的阈值语义、`id` 的重置规则（跨 session？）。

```
    │   └── metrics.py                # 覆盖率估算 + 结果落盘
    └── test/
        ├── fake_goal_server.py       # ⚠️ 见下
        ├── test_frontier.py
        ├── test_projector.py
        └── test_anomaly.py           # 站立/倒地两个 case
```

**为什么 `interfaces` 建议提到顶层**：接口 03 是 G2→G3 的**共用契约**，而仓库硬规矩是「别动别人的目录」。放在 G2 目录下，G3 要么构建别人目录里的包，要么每次接口变更都得找 G2。

**`fake_goal_server.py` 是 v1 的重要遗漏** —— `baseline/README.md` 明明白白写了自测手段：

> 「**G2 的探索节点对着一个假的目标接收器就能调**」

v1 的「不等任何人」清单里没有它。缺了它，状态机、黑名单、超时判据、震荡抑制（v1 自己说「不做必定震荡」）这些逻辑**在前 5 周根本无法被真正测到** ——「两条链都能提前跑通」就只剩一半。它还要能模拟**被抢占**场景。

### A/B 分工（v1 遗漏）

G1 的 README 明确写了两人怎么分，G2 一个字没有。建议：

## 八、风险与对策

| 等级 | 风险 | 对策 |
|---|---|---|
| **高** | **相机不提供 `sensor_msgs/Image` / `CameraInfo`**（可能是 H.264 流） | 第 1 周实物核实；准备好桥接/解码方案与自标定 |
| **高** | **预训练检测器在躺姿上召回未知**（COCO 缺躺姿样本） | 第 2–4 周实测 recall；结论决定是否微调 |
| **高** | 无深度相机（可能是 Air） | 路线 B 提前实现，但**先评估其 2–5 m 距离上限是否够用** |
| **高** | `use_sim_time` / QoS 配置错误 | 写进接口契约与 launch 模板；联调第一件事查 QoS |
| **高** | **G3 返航点抢占 G2 目标，双方打架** | 立 G3→G2 停手信号；状态机加 PASSIVE（见第十节） |
| **高** | **覆盖率/检出率口径未定** → 验收对不上账 | 第一周随接口 04 冻结（见第十节） |
| 中 | 机载算力不足 | 模型降档 + 抽帧；**TensorRT engine 必须在 Orin 上导出** |
| 中 | **真机机时排期**（v1 漏了，项目风险表明列） | 提前两周订机时；仿真验收通过再上真机 |
| 中 | frontier 目标点选到墙里 | BFS 测地 + 安全半径同源 |
| 中 | 目标点来回震荡 | 历史访问惩罚（必做）+ 失败黑名单 |
| 中 | 地图质量差 | 假地图先开发；加地图质量检查 |
| 中 | 目标点朝向错 → 白跑 | 显式设 yaw |
| 低 | TF 未就绪 | 假 TF 先跑通 |

**算力与存储纪律（v1 缺失）**：项目选题第一理由是「**基本不抢 GPU**」，G1 的 README 专门写了「**可无头运行**，别开着 GUI 吃资源」。G2 需要：仿真无头运行、错峰、批处理、注意磁盘占用（snapshot 相关见 5.3）。

> v1 建议「长时实验关掉 snapshot」会让接口 03 的「抓拍图」交付物**在长跑数据里直接缺失**。
> 更好的做法：**每个 `track_id` 只在新出现时带图**，或图落盘存路径。

**许可证**：ultralytics 是 **AGPL-3.0**。课程/学术用途没问题；若公开部署为服务或用于对外合作，AGPL 的网络条款要求公开完整源码（含权重）。

## 九、测试策略

| 层级 | 内容 | 何时 |
|---|---|---|
| 单元测试 | frontier（已知栅格断言位置 + 最小簇）；投影（**16UC1/32FC1 两种编码断言一致**）；**倒地判据（站立/倒地两个人工向量）**；增益排序 | 2–4 周 |
| 离线 | COCO 图片/视频跑检测；**距离-召回曲线**（见下） | 2 周起 |
| **异常验证数据** | **v1 缺失** —— 方法 A/B 都是判据，需含倒地姿态的数据验证。COCO 里基本没有。用公开跌倒数据集，或第 10 周在仿真/实验室摆拍采集 | 10 周前 |
| 回放 | rosbag 回放（复用接口 04 的配置） | 6 周起 |
| 仿真联调 | 接 G1 真地图 + 真 TF | 6 周起 |
| 指标验证 | 检出率 / 误检率（**须注明距离与 imgsz 前提**） | 13 周起 |

**距离-召回曲线（v1 缺失，很关键）**：COCO 预训练默认 `imgsz=640`。640×480 输入下，**20 m 外的人可能只有 20–30 px 高**，检出率会很低。v1 定了「检出率 > 85%」却没有 ① 检测距离范围的定义 ② `imgsz` 提升（960/1280）的算力代价 ③ 与「真机算力不足 → nano 模型」的冲突（**nano + 640 的远距离召回最差**）。这三件事必须一起谈，否则指标不可达。

**三维投影验证**：在仿真里放已知 `map` 系坐标的目标（如人在 (5,3)），跑完整链路比对真值。**必须在接真机之前做**。

## 十、待全队决定的事项 ⚠️

以下**不是 G2 组内能定的**，需要与 G1/G3（部分需老师）确认。建议第一周随接口冻结一并提出。

### 10.1 【契约空白】G3 → G2 的「停手信号」

**问题**：返航点由 G3 直接发 G1，与 G2 的探索目标**共用同一个 action server**。Nav2 一次只收一个 goal，G3 会抢占 G2 在飞的目标。契约里**没有** G3→G2 的任何接口（v1 虚构了一个，已删）。

**候选方案**（择一）：
- a. G2 订阅 `/battery_state` 自行进入 PASSIVE（不需要新接口，但**要猜 G3 的阈值**，语义隐式；且覆盖不到「急停」）
- b. **G3 发布任务状态，G2 订阅**（语义明确、可测试、与 G3 既有的状态机规划一致）—— **G2 推荐**
- c. ~~约定 G2 检测到「非自己发起的 cancel/abort」就进 PASSIVE~~ —— **已证伪，不可用**：
  查了 Humble 的实际 action 定义，`NavigateToPose` 的 result 是 `std_msgs/Empty`，
  没有任何 error_code；`GoalStatus` 只有 SUCCEEDED/ABORTED/CANCELED，
  **分不清「导航失败」和「被抢占」**。强行用会把正常失败误判成 PASSIVE，探索永久卡死。

> 完整论证（含时间轴、三条方案的对比、最小接口提议）见
> [`docs/议题-接口02返航抢占.md`](../../../docs/议题-接口02返航抢占.md)。

### 10.2 【指标】覆盖率与检出率的口径

- **覆盖率**：分母由谁定义？建议**仿真用 gz-sim world 真值导出可通行区域**（HTML 版明说「真机算加分而非必需」，仿真为主），**实时自算只用于监控，报告数字用真值口径**
- **检出率**：定义是「正确检出数 ÷ **场景内全部目标数**」，但**真值清单从哪来、谁记录、谁复核**，全文没有

- 责任人、截止时间、产出物 —— 现在全空

### 10.3 【交付物】冒烟检测怎么处理

- 是否**修改 `g2_vision_explore/README.md` 交付物 3 的验收标准**（现为「人员倒地、**设备冒烟**等在演示场景里能报出来」）
