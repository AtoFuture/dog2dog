## 1️⃣ 相机到底发什么

### 实测结论

```
/frontvideostream    unitree_go/msg/Go2FrontVideoData    ← 前视相机
```

⚠️ **这不是 `sensor_msgs/Image`**，是宇树自定义的**视频流**消息（`unitree_go` 包）。这意味着：

- 走不了 `cv_bridge` 那条标准通路，要用宇树的 SDK/解码方式
- **没有 `camera_info`** → 内参拿不到，只能自标定

> ❌ **没有** `/camera/...` 之类的标准相机话题。

### 规格（官方文档 + 社区实测）

| 项 | 值 | 来源 |
|---|---|---|
| **分辨率** | **1280×720（720p）** | 官方规格表（多处一致） |
| **视场角** | **120°** 超广角 | 官方规格表 |
| **官方帧率** | **15 fps**（App 图传档） | 官方文档 |
| **编码** | **H.264** | 实测（`00 00 00 01` 起始码 + `41 e0` NAL 头） |
| 消息里的三路 | `video720p` / `video360p` / `video180p` | 实测（消息定义） |

### ⚠️ 但 DDS 直读是**社区公认的坑**，不是我们配错了

实测现象和网上报告**逐字吻合**：

```
收到 22 帧 / 12 秒 -> 1.8 fps          ← 明显不对（官方 15fps）
rcutils: 'invalid data size, at rmw_cyclonedds_cpp/src/serdata.cpp:308'
rcutils: 'unable initialize generic sequence, .../serdata.cpp:311'
```

社区报告（`unitree_sdk2_python` issue #102 等）：

- 话题**看得见、能用 header 测出 ~31–34 Hz**，但**一取数据就失败**
- 报错就是上面那两条 CycloneDDS 的
- 有人把 `video720p` 直接 dump 成 `.h264` 只能解出顶部几行 —— **说明载荷不是能直接拼接的裸码流**

**官方/社区给的出路**（与我们无关，是这条路本身的坑）：

| 方式 | 说明 |
|---|---|
| SDK 的 `VideoClient` | 走 `videohub` 服务（API ID 1001 `ROBOT_VIDEO_API_ID_GETIMAGESAMPLE`），客户端**只有预编译**的 |
| WebRTC | `/api/videohub/request` —— **前人的 `baiyanggo_webrtc_bridge` 走的就是这条** |
| RTSP | `udpsrc address=230.1.1.1 port=1720 ! application/x-rtp, encoding-name=H264` |

> 📌 **这条反过来印证了「桥是必需的」**：前视相机的 DDS 直读不通，
> 是**上游就有的已知问题**，不是这台狗或这个实验室特有的。
> 见 §7 与「大消息静默」那条。

> 📌 顺带：有资料提到**某些 Go2 配置带深度相机（1280×720 @ 30fps）**。
> **我们这台没有**（`lsusb` + `/dev/video*` 双重确认）。
> 但这条说明**深度相机在 Go2 产品线上是有官方配置的** —— 对 §2 那个决策有用。

## 2️⃣ 有没有深度相机 —— ❌ 没有（硬件层面确认）

### 怎么确认的

```bash
lsusb           # USB 设备：只有一张 Realtek USB 无线网卡 + 根 hub
ls /dev/video*  # 一个都没有
```

**两条都指向同一个结论：物理上没有接任何摄像头。**

不是"驱动没起"——**是压根没有**。（`~` 下有个 `depth_camera_ws`，说明前人试过，但当前没接硬件。）

### 这对 G2 意味着什么 ⚠️

**G2 现在的整条三维链路在真机上跑不了：**

```
深度图 → 反投影 → 三维关键点 → 地面拟合 → 离地高度 → 床/地面双峰
  ↑
这里断了
```

这不是调参能解决的，**是方案层面的问题**。可选方向（需组内讨论）：

| 方案 | 代价 |
|---|---|
| 加装深度相机（D435i 之类） | 要买、要装、要标定外参；但链路原样可用 |
| 改用激光雷达点云 | 有 L1 点云，但点云密度远低于深度图，关键点取深度这一环要重做 |
| 退回单目 + 地面假设 | 精度掉一个量级，且违反"用姿态估计代替标注"的初衷 |
| 只做二维检测（交付物 1 降级） | 最省事，但交付物 3（倒地识别）基本作废 |

**建议尽快拉全队定这件事** —— 它比 fx、质检门那些都根本。

## 5️⃣ 相机安装位 —— 高度 ≈ 35 cm，俯仰 ≈ 0°（**名义值**）

**不用卷尺 —— 从官方 URDF + 机器人自报的机身高度推出来的。**

### 推导

```
① 官方 URDF（unitree_ros/robots/go2_description）里的相机安装点：
   front_camera_joint:  parent = base → child = front_camera (fixed)
   origin  xyz = "0.32715  -0.00003  0.04297"    rpy = "0 0 0"

② 机器人自己报的基座离地（/sportmodestate 的 body_height）：
   body_height = 0.3094 m

③ 合计：
   相机离地 = 0.309 + 0.043 = 0.352 m  ≈ 35 cm
   俯仰     = rpy(0,0,0) 相对基座 → 与机身平行 → 站立时 ≈ 0°（水平）
```

**与 G2 早先按 Go2 形态估计的「约 35 cm、接近水平」独立吻合。**

### ⚠️ 这是名义值，不是标定值 —— 现场要复核

- URDF 里的 `front_camera` link 是**空元素**（无 visual/collision），它的 origin 是**声明的参考系**，未必精确
- 实物相机模组的安装可能有细微差别
- `body_height` 随姿态变化，0.3094 是**正常站立**时的值

**→ G3 现场确认一遍；真正的标定是 G1 第 9–11 周的任务。**

### 🔴 这条对 G2 是硬阻塞

```
相机离地 0.35 m      vs      fit_floor_plane 要求的 [1.0, 3.0] m
```

**0.35 落在区间外 → 代码原样上真机会 100% 拒帧，而且不报错**，
只表现为"永远没有倒地结论"。

**必须把 `g2_core/floor.py` 的 `min_camera_height_m` 调到 0.35 以下。**

## 📌 盘点中发现的、超出清单范围的三件事

**① ROS2 版本是 Foxy，项目约定的是 Humble**

```
/opt/ros/foxy      ← 狗上
/opt/ros/noetic    ← 还有 ROS1
```

服务器的容器是 **Humble**。跨版本 DDS 通信与代码兼容性都**没验证过** —— 这是全队要拍板的事。

**② 狗上已经跑着 SLAM + Nav2，前人做了大量工作**

```
slam_toolbox   --params-file ~/nav_real/config/slam_toolbox_real.yaml
nav2_bringup   --params-file ~/nav_real/config/nav2_real.yaml
```

`~` 下还有 `cyclonedds_ws`、`unitree_sdk2`、`bags`、`nav_real`、`go2_agent_ws`、
`depth_camera_ws`、`go2_feishu_bot`、`qwen_robotnav` 等。

**→ G1 基本不用从零搭仿真，先去读这些配置。** 也说明这台狗**不是新的**，有历史包袱。

**③ 网络拓扑（影响所有远程操作）**

```
狗的机载电脑  eth0  192.168.123.18/24  ──0.15ms──> 控制电脑 192.168.123.161
              wlan0 192.168.3.107/24                （网关 192.168.3.1）
              tailscale0 100.121.216.97

服务器        10.31.112.43（实验室网）  +  tailscale0 100.92.162.45
```

⚠️ **实验室网 IP 直连不通**（狗的防火墙只放行 Tailscale 接口）。**远程一律走 Tailscale。**

**④ ⚠️ 原生雷达/视频的大消息 DDS 通路** —— **根因假设，待验证**

现象：小消息正常，大消息拿不到。

| 消息大小 | 例子 | 实测 |
|---|---|---|
| 小（几百字节） | `/sportmodestate` | ✅ 正常（`body_height` 就是这么读到的）|
| **大**（点云、视频） | `/utlidar/cloud`、`/frontvideostream` | ❌ 拿不到 / CDR 反序列化报 `invalid data size` |

**假设的根因**（`~/cyclonedds_ws/cyclonedds.xml`）：

```xml
<Internal>
    <!--MinimumSocketReceiveBufferSize>50MB</MinimumSocketReceiveBufferSize-->
</Internal>
```

**接收缓冲的设置被注释掉了** —— CycloneDDS 退回小默认值，大消息溢出丢包。
内核其实放行（`net.core.rmem_max = 52428800` = 50 MB）。

> ⚠️ **这是推论，不是实测结论。** 验证需要取消那行注释并重启 DDS ——
> **该操作会改动狗上的配置，未经许可不要做。** 验证前不要把它当定论引用。
>
> 🔴 **但有一条是确定的：`baiyanggo_webrtc_bridge` 是必需的。**
> （2026-09-18 实验室成员确认）
>
> 所以上面那条注释**不是**本问题的解法 —— 它只是"大消息走不通"这个现象的
> 一个**可能成因**，而前人已经判定：**绕过去（自建桥）才是这条路**。
>
> **不要把「取消注释就能删掉那座桥」当成待办** —— 那是错的。
> 具体原因待补（是试过无效，还是原生通路另有问题），问 `baiyang` 时一并确认。
> **在那之前：要用点云/视频，就走桥。**

## 已知会踩的坑（含本次实测新增）

| 坑 | 说明 |
|---|---|
| ⚠️ **狗上是 Foxy，`--once` 不存在** | `ros2 topic echo --once` / `ros2 topic hz` 的部分写法是 **Humble 才有**的。在狗上要写成 `timeout 15 ros2 topic echo <topic> \| head` |
| **读宇树消息要 source 对包** | 不 source `unitree_go` 的消息包，`ros2 topic echo /sportmodestate` 会抛 `get_msg_class` 的 traceback |
| **桥没起来时话题是空的** | 这个话题列表来自 `unitree_ros2` 的 DDS，不是原生 ROS2 |
| **QoS 配错一个包都收不到** | 能看到话题但收不到数据，八成是 QoS 不匹配 |
| **16UC1 vs 32FC1** | 搞错是 1000 倍深度差（本机无深度相机，暂时用不上） |
| **标称 ≠ 实物** | 本次就是靠这个发现"没有深度相机"的 —— 网上规格说有，实物没有 |
