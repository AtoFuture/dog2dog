# 课题 12 · 机器狗自主侦查 — 选题与实施方案

> 六人三组 · 十六周 · 共享八卡 4090（几十人共用）

---

## 一、选题结论

**课题 12：基于 SLAM 和目标检测的机器狗自主侦查算法开发**

### 1.1 横向比选结论

原始调研文档给出了 12 个课题。在「六人小组 + 算力为几十人共用的八卡 4090」这两个硬约束下，逐个评估：

| 课题 | 训练需求 | 结论 |
|---|---|---|
| 1 灵巧手 VLA | 多卡 VLA 训练 + 灵巧手真机 | 淘汰：抢卡 + 采数据双重死结 |
| 2 双臂双灵巧手 | 同上，且主基线仓库不存在 | 淘汰：需从零搭建 56 自由度系统 |
| 3 维修工具使用 | 灵巧手 + 力控 + 接触密集 | 淘汰：Sim-to-Real 极难 |
| 4 分层世界模型 | 世界模型训练成本极高 | 淘汰：指标模糊，引用本身有误 |
| 5 具身问答主动重建 | 中等，可纯仿真 | 备选：Habitat 3.0 环境配置磨人，基线对不上题 |
| 6 分布式多机器人重建 | NeRF/3DGS 训练，真占卡 | 备选：研究深度最好，但工程量最大 |
| 7 VLA 攻击与防御 | 7B 模型微调，评测是闭环 rollout | 淘汰：最小实验单元需连续数小时占卡 + 反复迭代 |
| 8 无人机赛事解说 | 视频大模型 + 自训检测器 | 淘汰：无人机视角赛事数据难搞，评价主观 |
| 9 实时三维重建 APP | 轻，重活在手机端 | 备选：需移动端开发能力 |
| 10 MoA 智能路由平台 | 零训练 | 最优算力友好，但偏工程集成、学术新意弱 |
| 11 VIO + 姿态判断 | 几乎为零 | 算力最友好，但领域饱和、创新空间小 |
| **12 机器狗自主侦查** | **CPU 为主，几乎不占卡** | **选定** |

### 1.2 选定理由

1. **绕开算力瓶颈**：SLAM（RTAB-Map）与导航（Nav2）跑 CPU；YOLO 直接用预训练 80 类权重，零训练成本；Gazebo 仿真一台带显卡的机器足够。几十人抢的 GPU，这个课题基本不碰。
2. **组件全部成熟**：`unitree_ros` 1566★（活跃）、`introlab/rtabmap` 3996★（活跃）、`ultralytics` 61688★（活跃）。不是 9★ 没人踩过坑的研究原型。
3. **有仿真兜底**：真机走不通时，Gazebo 里的完整自主侦查流程本身就是可交付成果。这是 12 个课题里风险对冲最好的。
4. **六人天然拆得开**：三组低耦合，可并行开工。
5. **硬件可用**：实验室有宇树 Go2，档期充足。

## 二、分组

### 2.1 切分原则

按**层**切，不按模块切。判据是耦合强度：**强耦合的东西必须在同一组，接口清晰的地方才切一刀。**

- SLAM 与 Nav2 **必须同组**——它们共享同一棵 TF 树（`map → odom → base_link`）和同一张 costmap。建图漂了还是导航配错了，在调试上分不开，硬拆两组只会互相甩锅。
- 「探索策略」**从导航里摘出来**交给 G2——它输出的是「下一个去哪」的目标点，不碰路径规划，属于决策层而非执行层。摘出来后 G1 与 G2 之间只剩一个接口：`NavigateToPose`。

### 2.2 三个小组

#### G1 · 建图导航（2 人）

| | |
|---|---|
| **职责** | 仿真环境 · SLAM · 定位 · Nav2 · 避障 |
| **任务** | ① Gazebo 场景、Go2 模型、传感器配置、批量测试脚本<br>② RTAB-Map 集成、IMU 与腿式里程计 EKF 融合、外参标定<br>③ Nav2 配置、costmap、路径规划、动态避障 |
| **交付** | 可运行仿真环境 · 栅格与点云地图 · TF 与定位输出 · 可执行的导航栈 |
| **目录** | `baseline/g1_mapping_nav/` |

> ⚠️ 三组里最重的一组。但活儿在时间上是串行的（仿真 1–4 周 → SLAM 3–8 周 → Nav2 7–12 周），两人可这样分：
> - **A**：仿真环境 → SLAM → 外参标定
> - **B**：Nav2 → 避障 → 真机调参
>
> 第 7 周之后两条线同时跑。若实际吃不消，唯一可外挪的是「仿真环境」（本质是公共基础设施），可考虑交给 G3 兼管平台。

#### G2 · 视觉探索（2 人）

| | |

## 三、接口契约（第一周冻结）

之后只加字段，不改语义。

| # | 方向 | 名称 | 内容 |
|---|---|---|---|
| 01 | G1 → G2 / G3 | 地图与定位 | `nav_msgs/OccupancyGrid` + `sensor_msgs/PointCloud2` + TF(`map → base_link`) |
| 02 | G2 → G1 | 探索目标点 | `NavigateToPose` action（探索目标点与返航共用同一入口） |
| 03 | G2 → G3 | 目标消息 | 自定义 `Detection3D`：类别 / 置信度 / 三维坐标 / 时间戳 / 抓拍图 |
| 04 | 全队 | 评测数据格式 | 统一 rosbag 话题清单 + 指标计算脚本，每次实验自动落盘 |

**接口 02 是关键**：它是 G1 与 G2 之间唯一的缝隙。视觉探索只发目标点，路线怎么规划、怎么绕障全归建图导航。

## 五、评测指标

| 指标 | 定义 | 建议目标 |
|---|---|---|
| 探索覆盖率 | 已建图面积 ÷ 可通行总面积 | > 90% |
| 建图精度 | 与激光扫描对比的绝对轨迹误差 ATE | < 0.15 m |
| 目标检出率 | 正确检出数 ÷ 场景内全部目标数 | > 85% |
| 误检率 | 错误检出数 ÷ 全部检出数 | < 10% |
| 单次任务耗时 | 从出发到完成侦查并返回基站 | 记录基线 |
| 返航成功率 | 低电量触发后安全返回的比例 | 100% |

> 覆盖率随时间的变化曲线是最有说服力的一张图——它同时体现探索策略与建图稳定性。

## 六、风险与预案

| 等级 | 风险 | 预案 |
|---|---|---|
| 高 | **足式平台建图漂移**（机身晃动导致点云匹配失败、回环误检） | 降低扫描速度、做足外参标定、调回环参数；兜底是仿真流程本身即为可交付成果 |

## 七、技术选型

### 7.1 对调研文档的三处修正

| 模块 | 文档写的 | 改用 | 原因 |
|---|---|---|---|
| SLAM | Cartographer | **RTAB-Map** | Cartographer 2024-01 已停更；RTAB-Map 3996★ 活跃维护，支持外观回环与三维点云，更适合足式平台 |
| ROS 驱动 | `unitree_ros` | **`unitree_ros2` / `unitree_sdk2`** | 前者是 ROS1 时代的老仓库，Go2 的 ROS2 支持在新仓库 |
| 目标检测 | YOLOv10 | **ultralytics 最新版** | 不必纠结版本号，`pip install ultralytics` 即用 |

其余：**Nav2**（ROS2 标准导航栈）+ **explore_lite** 或自写 frontier 插件 + **robot_localization**（IMU 与腿式里程计 EKF 融合）+ Gazebo 打底。

### 7.2 仿真路线选择（重要）

调研文档关于仿真只有一句话：

> 仿真环境：Unitree Gazebo官方仿真环境 + Unity，配置多种室内外场景和地形，支持足式动力学仿真

**这句话没有可操作性**——Gazebo 和 Unity 是两个不同的仿真器，"+"在一起是什么意思一个字没提。且全文 12 个课题的仿真部分都是同一个模板，每个只有一行，**没有任何一个课题给了步骤**。

核查宇树仓库后的实际情况：

| 仓库 | 内容 | 状态 |
|---|---|---|
| `unitree_ros` 1566★ | 有 `unitree_gazebo`（launch/plugin/worlds）+ `robots/go2_description` | **ROS1 时代** |
| `unitree_ros2` 830★ | 只有 cyclonedds_ws + example + docs，**无 Gazebo** | 纯通信层 |
| `unitree_mujoco` 1190★ | 官方 MuJoCo 仿真 | 主要给 RL 训练用 |

> **宇树官方有 Go2 的 Gazebo 仿真，但它是 ROS1 + Gazebo Classic 的；ROS2 那边官方只给了通信层。**

两条路：

- ✅ **路线 A（推荐）：ROS2 + gz-sim，自行移植 Go2 模型**
  - gz-sim 有现成的深度相机、IMU、激光插件；Nav2 与 RTAB-Map 都是 ROS2 原生，全链路顺畅
  - **仿真里调好的 Nav2 参数与 RTAB-Map 配置可直接搬到真机**（真机走 `unitree_ros2`，同一技术栈）
  - 代价：Go2 的 URDF → SDF 转换与传感器挂载需自己弄，前期约 1–2 周
  - 算力友好：gz-sim 可无头运行，不占共享卡
- ⚠️ **路线 B：Gazebo Classic + `unitree_ros`，官方开箱即用**
  - Go2 模型与 world 现成，最快看到画面
  - 但 Gazebo Classic 已 EOL，且是 ROS1——**Nav2 用不了**，得退回 `move_base`；RTAB-Map 也只能用 ROS1 版
  - 与真机部署的技术栈是断的，仿真里调好的东西搬不过去

**不建议**：Isaac Sim（吃 GPU 且跑仿真时独占，对共享八卡不利）；MuJoCo（物理准但传感器仿真与 ROS2 集成弱，跑不了 Nav2/SLAM 全链路）。

### 7.3 设备盘点清单（第 1 周，由 G3 执行）

**为什么必须先做**：仿真里挂什么传感器，直接决定后续所有算法选型。搞错了就是返工。这与老师要求的"先在仿真里做"不冲突——它是仿真的前置输入。

| # | 要弄清什么 | 为什么关键 |
|---|---|---|
| 1 | **型号**：Air / Pro / Edu / X？ | 不同版本传感器配置完全不同，Air 没有激光雷达 |
| 2 | **传感器清单**：激光雷达？深度相机？IMU？前视相机？ | 直接决定 SLAM 走激光还是视觉 |
| 3 | **机载算力**：有没有 Jetson Orin？ | 决定 YOLO 跑机上还是回传 |
| 4 | **SDK 权限**：关节级接口还是只有高层速度指令？ | 决定仿真控制层做到哪一级 |
| 5 | **相机安装位**：高度、俯仰角、离重心偏移 | 外参不复现，仿真调好的参数上真机全偏 |

**怎么弄清**：把狗拿出来跑一次官方 demo，然后敲两条命令：

```bash
ros2 topic list      # 真机到底发布了哪些话题
ros2 topic hz /xxx   # 关键传感器的实际频率
```

这比看说明书准得多，能发现实际配置与标称配置的差异。顺手把传感器安装位置拍照片、量尺寸。

| 真机实际情况 | 仿真里就要体现 | 技术选型随之变成 |
|---|---|---|
| 有激光雷达 | gz-sim 挂 GPU 激光插件 | SLAM 走激光为主，更稳 |
| 只有深度相机 | 仿真相机内外参 + 深度噪声 | RGB-D SLAM，重点在视觉特征 |
| 有 Orin 机载算力 | 按机载算力设帧率上限 | YOLO 用 nano/small 量化版 |
| 无算力需回传 | 加通信延迟、带宽约束 | 数据回传策略变成设计点 |
| 只有高层速度接口 | 仿真只到速度指令层 | 导航栈按差速模型配 |
| 开放关节级控制 | 可仿真关节级 | 才谈得上步态相关优化 |

> ⚠️ 如果盘下来是 **Air 版、没有激光雷达**，课题难度会明显上升——纯视觉 SLAM 在足式平台上本就比激光难做（机身晃动、纹理缺失场景容易丢）。这种情况需回头调整方案，把重点放到深度相机 + 更保守的建图策略上。**越早盘越好。**

## 八、加分项

**多机协同侦查**：在仿真里跑单个 Go2 的多个实例，不需要第二台真狗。能给出「覆盖时间 vs 机器人数」曲线，把分布式任务分配借过来，正好补上课题 6 的内容。

**异常行为识别**：用姿态估计代替标注——人体长宽比与躯干朝向判倒地，无需额外标注数据，零训练成本。让「侦查」从找人升级到判断异常。
