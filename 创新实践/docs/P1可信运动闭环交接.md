## 二、接手前必须补的三处改动

**这三处不在本仓库里。** 拿一台新机器从 `develop` 复现，缺了它们跑不起来：

| 位置 | 改什么 | 为什么 |
|---|---|---|
| `ROS2-Gazebo-GO2/src/gazebo_sim/launch/launch.py` | 加受 `GZ_HEADLESS` 控制的 `-s`，并在无头时转发子 launch 的 `enable_rviz` 开关 | 原文件把 `gz_args` 写死 `-r -v4`，没有无头入口；不关 rviz2 的话它在无 DISPLAY 下 abort，会带崩整个 launch |
| `~/go2_sim_ws/run_sim_iso.sh` | 加 `GZ_HEADLESS` 传递 + EGL vendor 修复 | 见下 |
| `~/go2_sim_ws/g1ros.sh` | 新建（隔离域里跑 ROS 命令的入口） | 隔离三元组里 `ROS_DOMAIN_ID` / `IGN_PARTITION` 必须在**容器内**设置，漏设会静默连到别人的仿真 |

⚠️ **`~/go2_sim_ws/` 下的脚本不属于任何 git 仓库**，换机器就丢，建议尽快纳入版本管理。

### EGL 那个坑值得单独说

无头起仿真后传感器渲染线程刷屏 `libEGL warning: egl: failed to create dri2 screen`，
然后 SIGSEGV。根因不是配置，是 **enroot 只注入 NVIDIA 的 `.so`、不注入 glvnd 的
EGL vendor 配置**——容器里 `/usr/share/glvnd/egl_vendor.d/` 只有 `50_mesa.json`，
于是 EGL 被派发给 Mesa 走 DRI2（那是需要 X 的路径）。

解法不动容器镜像：把 `10_nvidia.json` 放进已挂载的 `/tmp`，
用 `__EGL_VENDOR_LIBRARY_FILENAMES` 指过去。
另外**必须用 `~/.enroot/ros-gui` 容器拿 GPU 库**，纯 `ros` 容器里根本没有
NVIDIA 图形库（实测少了 libnvidia-glcore 等 41 个库）。


## 四、三个会静默污染结论的坑

### 1. `joint_group_controller` 会停在 `unconfigured`，狗一动不动

现象极具迷惑性：**仿真看着全好**——`/clock` 在走、节点齐全、
`commands` 话题发布者数 = 1、`quadruped_controller` 以 29 Hz 照发命令，
但真值净位移 0.0000 m、z 恒在生成高度 0.446 而非站立 0.27。

根因是控制器没被激活（launch 里的 spawner 有竞态）。`configure_controller` 可能返回
`ok=False`，但 `switch_controller` 能激活。`start_nav2_isolated.sh` 第 1 步会自检并停下。

### 2. action 的 `SUCCEEDED` 不能当到达判据

实测有一轮 action 报 `SUCCEEDED` 而真值在 **0.362 m** 外。
因为 **goal checker 判的是 AMCL 的位姿，不是真值**，而当时 AMCL 对真值偏了 0.464 m。

根因是 AMCL 更新太稀：`update_min_d: 0.25` / `update_min_a: 0.2` 意味着要动 25 cm
或转 0.2 rad 才更新一次，实测约 0.3 Hz，两次更新之间 goal checker 拿的是陈旧估计。
`transform_tolerance: 10.0` 还允许超时使用 10 秒前的变换。三个值都已收紧。

**反过来也要警惕**：后来有一轮 G5 物理上到了（0.115 m）但 action 在 80 s 内没报成功——
「报成功没到」和「到了没报成功」都会出现，**两个方向都要核**。

### 3. 速度指令被放大 ~10 倍

`cmd_vel_pub.py` 里 `multiply_and_limit` 的 scale 被从上游的 `0.035` 改成了 `0.3`
（**这是仿真工作区里一处我们没动过、也没提交的改动**），而步态对 rv 的增益本身约 10 倍。
合起来 Nav2 按配置发 0.26 m/s，实际会跑出 ~2.7 m/s、rv 顶到 0.27，
远超实测稳定边界 **rv < 0.04**（cmd 0.06 档就原地蹬腿不前进，路径 1.9 m 净位移 0.03 m）。

`tools/cmd_vel_scaler.py` 的系数 0.115 与上游 0.035 相乘 ≈ 0.0345，
**本质上是把我们这一路恢复到上游默认值**。缩放只落在我们这份配置里，共享代码未动。

## 补充 · 2026-09-24（复算证据包后的修正）

拿 `/home/wy/g1_bags/p1_20260923/` 里的包在容器里重算了一遍，结论与改动如下。

### 1. G5 的 action 未收敛：根因是缩放器的死区，不是终点朝向容差

把 amcl_G5 那一轮（goal `(8.00, 3.50)`）的真值逐秒拉出来：

```
 t=3.9~9.0s   原地转身（11°→90°）
 t=11.4~55.4s 完全冻结 44 s —— 位置与朝向逐位相同
 t=55.6s 起   重新转身 → 12 m 直行 → t≈90s 停住
```

冻结期间 Nav2 每秒都在 `Passing new path to controller`，但：

```
cmd_vel_scaled_out  lx = 0.01368
cmd_vel             lx = 0.0000      ← 被死区抹平
```

`cmd_vel_scaler.py` 原来的 `deadband=0.002` 判在**缩放之后**的域上，
等价于把 Nav2 的 `0~0.0174 m/s` 整段抹成精确的 0，而 DWB 此时的输出正是 0.0137。

连锁：冻结 → progress checker 两次 `Failed to make progress` → 恢复+重规划 →
到点耗时 **86 s**，比 80 s 测试预算晚 6 s，所以 CLI 报超时；
而包里 `_action/status` 最终是 `SUCCEEDED`（其他 4 轮只要 13~26 s）。
**「报成功没到」和「到了没报成功」两个方向都真实存在，但这一轮是后者。**

### 3. 几处会误导接手人的地方

  `amcl_G2..G5` 才是第 1~4 轮。靠 nav2 log 的 `Begin navigating` 时间对齐才能解开。

  而 `nav2_scaled.launch.py` 加载的是仓库那份 → 那 5 轮跑的是 10.0。已对齐成 60.0。
- **`goal_test.sh` 原来不做判定**：只 echo 一次真值到 `goal_end_gt.txt`，不与目标点比，
  该文件出现过 0 字节（真值读失败）脚本仍 exit 0。现改为收尾调用 `goal_check.py`。
