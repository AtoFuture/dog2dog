## 🔴 高：判据会把失败判成通过 / 把通过判成失败

### H1. `map_growth.py:112` —— P1 第 5 项判据方向反了 ✅ 已修 2026-10-11

```python
"not_constant": {"value": growing, "pass": 0 < growing < steps}
```

`pass` 要求 `growing < steps`，即**至少有一次相邻更新「没长」**。而标签写的是
「增长率非恒定（覆盖率曲线非恒定）」——一个说的是"有没有断"，一个说的是"快不快得均匀"。

**已复现**（照抄第 96–125 行判定逻辑，喂合成数据）：

| 场景 | 在长比例 | 判定 |
|---|---|---|
| 狗一路走、地图每次更新都在长（**正是要证明的**） | 11/11 | **不通过 ❌** |
| 只长一次、之后 11 条完全不变 | 1/11 | **通过 ✅** |
| 只有 2 条地图消息、确实长了 | 1/1 | **不通过 ❌** |

第三行是另一处：`steps = max(len(rows) - 1, 1)`，两条消息时 `steps == 1`，
`0 < growing < 1` 恒假。

**为什么至今没暴露**：仓库 23 个包**没有一个**存到超过 1 条地图消息（全是 AMCL 静态图），
这个判据还没吃过一次真实输入。

**判定方法**：`python3 tools/map_growth.py <含多条 /robot1/map 的 bag>`，
看「更新中在长的比例」是 `N/N` 时是否报不通过。

### H3. `goal_test.sh:18,71,90-95` —— 脚本恒 `exit 0` ✅ 已修 2026-10-11

`set -uo pipefail` **没有 `-e`**；结尾是

```bash
if [ "${CHECK_RC}" -ne 0 ]; then echo "..."; fi
```

bash 对条件为假的 `if` 复合语句返回 0。所以 `goal_check.py` 判 `rc=1`（或 `rc=2`，
包里根本没真值）时，脚本只在 stdout 打一行，**自己仍 `rc=0`**。
任何用 `||`、`&&`、`set -e`、`$?` 串联的自动化都会把「未通过」记成通过。

`ACTION_RC`（第 71 行）取了但从头到尾没参与任何判断，也是死的。

**判定方法**：`bash tools/goal_test.sh ... ; echo $?`，对一轮必然失败的目标也应得 0。

### 🔴 N2. DWBLocalPlanner 对 TF 时间同步零容错，已替换为 RegulatedPurePursuit

**根因**：Gazebo 的 `use_sim_time` 与 TF 变换时间戳不完全同步，
实测偏差 0.7–7 秒。DWB 需要将全局路径转换到局部代价地图帧，
对 TF 时间精度要求高，完全无法工作。

**错误日志**：
```
None of the points of the global plan were in the local costmap
No valid trajectories out of 419!
Controller patience exceeded
```

**已修**：`go2_nav2.yaml` 中 `FollowPath` 插件从 `dwb_core::DWBLocalPlanner`
改为 `nav2_regulated_pure_pursuit_controller::RegulatedPurePursuitController`。
后者直接跟随路径，对 TF 时间容差更高（`transform_tolerance: 1.0`）。

**代价**：RegulatedPurePursuit 不做轨迹采样评估，避障能力弱于 DWB。
实测中 `use_collision_detection: true` 开着，但急转场景未压力测试。

**验证结果**（AMCL + 静态地图，速度渐变开启）：

| 目标点 | 结果 | 到达位置 | 误差 |
|---|---|---|---|
| (3.0, 0.0) | SUCCEEDED | (3.09, -0.01) | 0.09 m |
| (5.0, 0.0) | SUCCEEDED | (5.42, -0.03) | 0.42 m |
| (5.0, 3.0) | SUCCEEDED | (5.26, 3.14) | 0.32 m |
| (0.0, 0.0) | 超时未完成 | (-0.17, -0.59) | 0.62 m |

### 🟡 N3. 速度渐变插值有安全隐患：Nav2 停发后狗不停 ✅ 已修 2026-10-15

`cmd_vel_scaler.py` 新增了 50 Hz 定时器 `_ramp_loop`，**不管有没有新输入都发布**。
`_on_cmd` 只更新 `_target_lx` / `_target_az`，不发布。

**问题**：如果 Nav2 崩溃、被 kill、或进入 recovery 停止发布 `cmd_vel_scaled_out`，
`_target_*` 保持最后一个值，**机器狗会继续按最后目标速度移动**。

**触发条件**：Nav2 controller_server 进入 recovery（spin/backup）时
会停止发 FollowPath 输出；如果 recovery 期间 target 没被清零，狗会继续走。

**✅ 已修 2026-10-15**：`cmd_vel_scaler.py:91` 加 `cmd_timeout` 参数（默认 1.0s）；
`_ramp_loop`（`:154-156`）检测 `now - _last_cmd_time > cmd_timeout` 时将 `_target_lx`/`_target_az` 清零渐变拉回 0；`_on_cmd`（`:181`）更新 `_last_cmd_time`。

### 🟡 N4. 机器狗导航速度过慢（用户反馈"特别特别慢"）

**链路**：Nav2 发 0.26 m/s → `linear_scale=0.115` 缩放 → 0.030 m/s
→ `cmd_vel_pub` → rv≈0.030 → 步态 → 实际约 0.2 m/s

**根因**：步态稳定边界是 rv < 0.04（rv=0.06 时原地蹬腿），
所以 `linear_max` 被压到 0.030，实际速度只有 0.2 m/s。
5 m 目标需要约 25 秒，加上渐变加速时间更长。

**渐变参数影响**：`linear_accel=0.060`，`dt=1/50=0.02s`，
每步 `max_step=0.0012`，从 0 到 0.030 需要 25 步 = 0.5 秒。
渐变本身不是瓶颈，**瓶颈是 `linear_max` 太小**。

**可能的改进方向**（需要实测标定）：
1. 标定更高 rv 下的步态稳定性（rv=0.04~0.05 是否真的不稳定？）
2. 优化步态控制器参数，提高稳定边界
3. 如果 rv=0.04 可用，`linear_max` 可提到 0.04，速度提升 33%

### 🟡 N6. 速度渐变 `_ramp_step` 减速判定有边界 case

```python
rate = decel if abs(target) < abs(current) else accel
```

当 `current = 0.030`（正向最大）、`target = -0.030`（反向最大）时，
`abs(target) == abs(current)`，用 `accel` 而非 `decel`。
这意味着**反向切换时用加速率**，可能产生速度突变。

实际影响有限（Nav2 很少发反向指令），但逻辑不严谨。

### 🟡 N7. 角速度渐变没有 decel 参数 ✅ 已修 2026-10-15

self._current_az = self._ramp_step(
    self._current_az, self._target_az,
    self._angular_accel, self._angular_accel  # ← accel 和 decel 相同
