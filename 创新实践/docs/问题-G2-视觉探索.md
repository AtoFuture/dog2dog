## 🔴 高

### H1. `g2_core/projector.py:467` —— 飞点未过滤，远处的人系统性消失

```python
valid = np.isfinite(sub) & (sub > 0)          # 只挡 0 和 NaN，没有深度下限
```

对照同文件 `:379`（`sample_depth_near`）：

```python
valid = patch[np.isfinite(patch) & (patch >= min_depth_m)]   # 加了下限
```

**同一个作者、同一个文件，关键点那条路加了，bbox 这条漏了。** 这不是设计取向。

飞点是「非零但极小」的像素（`projector.py:221-243` 实测：全体像素约 2.4%，
峰值在 0.1~0.4 m），全部通过 `sub > 0` 混进 `z`。而 `:518` 的
`p98_z_dev = percentile(|z − median(z)|, 98)` 取的正是**尾部**——
只要飞点占比 ≥2%，第 98 百分位必然落在飞点堆里，
而飞点到目标的距离差 ≈ **目标距离本身**。

**实测**（直接调 `project_depth_bbox`，均匀平面 + 注入 0.05~0.6 m 飞点）：

| 目标距离 | 飞点占比 | dispersion | 结果 |
|---|---|---|---|
| 1.5 m | 2.5% | 1.01 | 接受 |
| 3.0 m | 2.5% | 2.50 | 接受 |
| **4.0 m** | 2.5% | **> 3.0** | **丢弃** |
| **6.0 m** | 2.5% | **> 3.0** | **丢弃** |
| 任意 | 0% | 小 | 接受 |

即 `dispersion ≥ 目标距离 − 0.6`。这个下界与物体实际尺寸无关，因此
**`max_dispersion_m = 3.0` 等价于一道 ~3.6 m 的距离门**。

触发场景：真实 RGB-D（结构光/ToF，正是仓库那两份素材的相机）上任何 ≥4 m 的人。
远处目标的 bbox 里轮廓占面积极大，而飞点恰恰沿轮廓分布
（`:242-243` 实测躺着的人 35×35 窗口飞点占 5.87~9.72%）——**越远越必丢**。
后果是 `proj_fail += 1`（`:472`）后 `continue`，**不报错、不告警、日志干净**。

**顺带污染了文档**：`projector.py:416-441` 那张标定表
（中位 1.58 / 最大 3.25 / 通过率 0.5→0%、2.0→74%、3.0→89%）把离散度归因为
「一个人身体自身的深度跨度就有 1.5 m 量级」。用数字反推这个归因站不住：
p98（不是 max）要取到 1.58，就得有 2% 以上的像素离中位数 1.58 m，
一个 1.4~3.3 m 处的人体给不出这个数；而按「dispersion ≈ 距离 − 0.6」算，
2.0 门限应放过 2.6 m 以内、3.0 门限放过 3.6 m 以内——与实测 74% / 89% 同量级。
**那张表量到的主要是距离，不是「这团像素是不是同一个物体」。**

**判定方法**：造一个人形目标放在 4 m 外，看 `Detection3D` 是否产出。

### H2. `g2_core/explorer.py:162` + `:85-109,425` —— 探索到后期站在门口不动且无人知道

`min_frontier_area_m2 = 0.25`。在 G1 实图分辨率（0.05 m/格）下，
frontier 条带按 1 格深算，要过门槛得**长 5 米**：

| 门洞宽度 | 条带格数 | 面积 | 判定 |
|---|---|---|---|
| 0.8 m | 16 | 0.040 m² | ❌ |
| 1.0 m | 20 | 0.050 m² | ❌ |
| 1.2 m | 24 | 0.060 m² | ❌ |
| 2.5 m | 50 | 0.125 m² | ❌ |
| **5.0 m** | 100 | 0.250 m² | ✅ 刚好 |

**`explorer.py:95` 的 docstring 自己就写着**「小簇恰恰是**真实门洞**的样子：
`min_frontier_area_m2` 取 0.25 m²」——知道，但默认值从没按实际分辨率调过。

后果：探索末期剩下的正是门洞这种小簇 → 每 2 秒
`IDLE → SEND_GOAL → SMALL_FRONTIERS → IDLE` 空转，**一个点不发、日志干净、
进不了 DONE**。比原先「误判 DONE 永久停机」好，但**仍然是站在那儿不动且无人知道**。

### H3. `g2_core/explorer.py:107-108` —— 契约要求节点计数告警，义务没实现

`:107-108` 明写：「这一条要靠调用方自己的计数/日志去发现（**节点侧应当计数并告警**）」。

实际：`explorer_node.py:299` 的失败路径只打 `debug("本轮没发点（{phase}）")`，
**连状态值都不打**，默认 INFO 级别下完全不可见；没有计数器；
`state_machine.anomalies` 从没被节点读过。

配套：`explorer_node.py:193` 是 `GoalSelector(ExplorerParams())` **硬编码默认值、
无 yaml** → 文档给的补救「调小阈值」在节点侧**做不到**，
安全半径与 G1 的 `inflation_radius` 也没有同源。

### H4. `vision_detector/detector_node.py:199-205` + `qos.py:49-54` —— CameraInfo 的 QoS 与真机驱动很可能不兼容

用 `LATCHED_QOS`（RELIABLE + TRANSIENT_LOCAL）订阅 camera_info。
而真机相机驱动按 ROS2 惯例用 `SensorDataQoS`（BEST_EFFORT + VOLATILE，
realsense2_camera 的 `camera_info_qos` 默认即 `SENSOR_DATA`）。

不兼容 → **一帧内参都收不到** → `self._intrinsics` 恒为 `None` →
`detector_node.py:406-411` 每帧 `return` → `frames` 永远为 0 →
**一条 `Detection3D` 都发不出去**，三维解算与倒地判据**全部失效**。

`qos.py:19-23` 那张「各话题约定」表里**根本没有 camera_info 这一行**，
而同文件 `:6-14` 还在强调「QoS 不匹配是 ROS2 视觉节点最常见的『一帧都收不到』，
而且它不报错」——相机内参订阅是这份文档唯一的例外。

对照组：`replay_images.py:128` 用 `LATCHED_QOS` 发 CameraInfo →
**回放链路永远是通的**，所以这个不匹配在自己的测试里绝不会暴露。

**判定方法**（一条命令）：`ros2 topic info /camera/color/camera_info --verbose`，
看 Publisher 的 Reliability / Durability。只要是 BEST_EFFORT 或 VOLATILE，本条必现。

### H5. `vision_detector/detector_node.py:234-237` —— 最主流的失效没有任何输出

```python
st = self._stat
if st["frames"] == 0:
    return
```

同一处 `:231` 的注释写着这个定时器是「每 10 秒报一次处理统计——出问题时一眼能看出卡在哪一步」。

QoS 不匹配（H4）、话题名不对（M2）、slop 太小、时间戳对不上时，`frames` 恒为 0 →
**统计行、`proj_fail` 分解、倒地统计行、所有告警全部不打印**，节点每 10 秒一声不吭。
唯一线索是 `:392-397` 那条**一次性** info（「收到第一对同步图像」）——
那条日志的**缺席**才是信号，而中控在节点起来之后才 attach，
看到的就是彻底的安静，**和「场景里没人」完全一样**。

这个 `if` 把两种性质完全不同的状态合并成了一条沉默路径：
「节点刚起来，帧还在路上」（暂时）和「QoS/话题不匹配，永远不会有帧」（永久）。
