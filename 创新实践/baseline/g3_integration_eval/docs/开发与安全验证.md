# G3 状态机：开发与安全验证

## 当前安全边界

- 四个逻辑状态：`STANDBY`、`EXPLORE`、`RETURN`、`ESTOP`。
- 订阅可配置的 `sensor_msgs/msg/BatteryState` 话题；默认 `/robot1/battery_state`。
- 向 G2 发布 `/mission_state`：`standby / exploring / returning / estop`，使用可靠、瞬态本地 QoS；`/g3/state` 继续保留大写内部状态。
- 只有 `EXPLORE` 状态且 `percentage` 严格小于阈值时才自动进入 `RETURN`；默认阈值 `0.20`。
- `STANDBY`、`RETURN`、`ESTOP` 会忽略低电量触发，因此同一轮低电量不会重复触发，`ESTOP` 也不会被低电量覆盖。
- `present=false`、`NaN`、无穷值以及不在 `[0.0, 1.0]` 内的电量读数会锁存电量故障并进入 `ESTOP`；收到新的有效电量前拒绝 `reset`。
- `RETURN` 的目标由 `NavigateToPoseClient` 构造，**发不发由 `enable_navigation_transmission` 决定，默认关闭**。
- 关闭时只打印目标预览，不等待 action server、不发送 goal，同时向 `/g3/return_event` 发一条 `status=preview` 事件，行为与之前的硬禁用一致。
- 开启后才会非阻塞地等待 `navigate_action`（最长 `navigation_server_timeout_sec`）、发送 home pose，并把每次尝试的每个状态写成 `/g3/return_event` 事件。
- 发送路径的唯一入口是 `request_return()` 中的 `send_goal_async()`，位于关闭分支提前返回之后，即关闭态下不可达；`send_goal()` 已随预览骨架一并移除。
- `ESTOP` 和离开 `RETURN` 会异步取消 G3 当前返航 goal；请求尚未 accepted 时先标记取消，迟到 accepted 后立即调用 `cancel_goal_async()`。取消到达 action 终态前拒绝 `reset`。
- 这里解决的是 Nav2 任务层停止，不等同于 Go2 的物理急停。接入真机控制前必须保留官方急停手段。
- 开发运行统一使用隔离域 `ROS_DOMAIN_ID=142`，不要在共享 Domain 42 上运行测试节点。

## 参数

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `battery_topic` | `/robot1/battery_state` | `BatteryState` 输入话题 |
| `low_battery_threshold` | `0.20` | 合法范围 `[0.0, 1.0]`，只有严格低于该值才触发 |
| `command_topic` | `/g3/command` | 状态机命令话题 |
| `state_topic` | `/g3/state` | 当前状态输出话题 |
| `mission_state_topic` | `/mission_state` | 发给 G2 的小写任务状态；可靠、瞬态本地 QoS |
| `navigate_action` | `/robot1/navigate_to_pose` | 返航 goal 的 action 入口；仅当发送开关打开时才会被真正调用 |
| `return_event_topic` | `/g3/return_event` | 返航尝试事件输出话题（`std_msgs/msg/String`，内容为 JSON） |
| `enable_navigation_transmission` | `false` | 返航发送总开关；只有显式设为 `true` 才会发送 goal |
| `navigation_server_timeout_sec` | `2.0` | 等待 action server 的超时，必须为有限正数，否则构造客户端即报错 |
| `home_frame` | `map` | home target 坐标系 |
| `home_x` / `home_y` / `home_yaw` | `0.0` | home target 位姿，yaw 以弧度给出、内部转四元数 |

可在启动时覆盖电量话题和阈值：

```bash
ros2 run g3_integration_eval g3_state_machine --ros-args \
  -p battery_topic:=/test/battery_state \
  -p low_battery_threshold:=0.25
```

Gazebo 连续耗电联调使用 G3 独立话题，避免与 G1 固定 80% 的假 BMS 冲突：

```bash
ros2 run g3_integration_eval sim_battery --ros-args \
  -p use_sim_time:=true \
  -p initial_percentage:=0.23 \
  -p idle_drain_per_sec:=0.0001 \
  -p moving_drain_per_sec:=0.001

ros2 run g3_integration_eval g3_state_machine --ros-args \
  -p use_sim_time:=true \
  -p battery_topic:=/g3/sim_battery_state \
  -p enable_navigation_transmission:=true
```

返航成功后自动恢复仿真电量到 80%：

```bash
bash g3_integration_eval/scripts/run_sim_battery_auto_recharge.sh \
  -p initial_percentage:=0.23 \
  -p idle_drain_per_sec:=0.0001 \
  -p moving_drain_per_sec:=0.001
```

脚本启用 `auto_recharge_on_return_success`，仿真电池节点只在
`/g3/return_event` 收到 `succeeded` 时将电量提高到 `0.80`。该功能默认
关闭且不影响真机电池桥接。回充完成后 G3 仍处于 `RETURN`，需要人工发送
`standby` 后才能开始下一轮探索。

`sim_battery` 订阅 `/robot1/cmd_vel`，默认以 2 Hz 发布。运动指令超过
`motion_epsilon` 后使用 `moving_drain_per_sec`，否则使用
`idle_drain_per_sec`；所有速率都是每秒减少的 0–1 电量比例。

真机的 Unitree `/lowstate` 不是 `BatteryState`，需先启动 G3 适配节点：

```bash
source /path/to/unitree_ros2/cyclonedds_ws/install/setup.bash
ros2 run g3_integration_eval unitree_battery_bridge
```

该节点默认将 `/lowstate` 的 `bms_state.soc`（0–100）转换后发布到
`/robot1/battery_state`（0–1）；仿真若已直接发布 `BatteryState`，不要再启动适配节点。

## Domain 142 低电量安全验证

以下所有终端都必须显式设置 `ROS_DOMAIN_ID=142`。不要 source 或停止共享 Domain 42 的仿真进程。

终端 A：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source /tmp/g3_eval_colcon/install/setup.bash
export ROS_DOMAIN_ID=142
ros2 run g3_integration_eval g3_state_machine
```

终端 B（观察状态）：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source /tmp/g3_eval_colcon/install/setup.bash
export ROS_DOMAIN_ID=142
ros2 topic echo /g3/state std_msgs/msg/String
```

终端 C（先进入探索，再发布模拟低电量）：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source /tmp/g3_eval_colcon/install/setup.bash
export ROS_DOMAIN_ID=142
ros2 topic pub --once /g3/command std_msgs/msg/String '{data: explore}'
bash g3_integration_eval/scripts/publish_test_battery.sh 0.20
bash g3_integration_eval/scripts/publish_test_battery.sh 0.19
```

预期结果：

1. `0.20` 等于阈值，不触发；状态仍为 `EXPLORE`。
2. `0.19` 低于阈值，只触发一次 `EXPLORE -> RETURN`。
3. 节点日志依次出现：

   - `low battery detected: ...; requesting RETURN`
   - `NAVIGATION TRANSMISSION DISABLED: preview only; action=/robot1/navigate_to_pose, frame=map, ...`
   - `RETURN navigation event: status=preview, goal_id=none, attempt_id=<hex>`

   不会出现导航 action 的 accepted/result 信息。

再次发布更低读数验证不重复触发：

```bash
bash g3_integration_eval/scripts/publish_test_battery.sh 0.18
```

状态保持 `RETURN`，不会再次打印状态切换或返航目标预览。

验证 `STANDBY` 不触发：

```bash
ros2 topic pub --once /g3/command std_msgs/msg/String '{data: standby}'
bash g3_integration_eval/scripts/publish_test_battery.sh 0.10
```

状态保持 `STANDBY`。

验证 `ESTOP` 优先级：

```bash
ros2 topic pub --once /g3/command std_msgs/msg/String '{data: explore}'
ros2 topic pub --once /g3/command std_msgs/msg/String '{data: estop}'
bash g3_integration_eval/scripts/publish_test_battery.sh 0.01
```

状态保持 `ESTOP`，低电量消息不能把它改成 `RETURN`。若有返航 goal，必须先观察到 `canceled` 终态；若由电量错误触发，还必须先收到新的有效电量。之后才可发送 `reset` 回到 `STANDBY`：

```bash
ros2 topic pub --once /g3/command std_msgs/msg/String '{data: reset}'
```

## 返航事件契约

每次 `RETURN` 尝试都会在 `/g3/return_event` 发若干条 `std_msgs/msg/String`，`data` 是紧凑 JSON：

| 字段 | 说明 |
|---|---|
| `schema_version` | 当前为 `1`，用于离线评估判断字段兼容性 |
| `attempt_id` | 本次尝试的本地唯一 ID；离线评估按它去重，同一尝试的多个状态共享同一 ID |
| `status` | 见下方状态链 |
| `goal_id` | Nav2 goal UUID 的 hex；只有在收到接受/拒绝响应后才非空，`preview` 与 `server_unavailable` 为 `null` |
| `trigger` | `battery`（低电量自动）或 `command`（命令触发） |
| `timestamp` | ROS 时钟的 `{sec, nanosec}` |
| `action_name` | 本次使用的 action 入口 |
| `home_target` | `{frame_id, x, y, yaw}`，便于离线核对目标是否被改过 |
| `detail` | 仅失败事件携带，记录异常文本 |

状态链：

```text
关闭态： preview

开启态： waiting_for_server ─┬─> server_unavailable
                            └─> goal_request_sent ─┬─> rejected
                                                   └─> accepted ─┬─> succeeded
                                                                 ├─> aborted
                                                                 ├─> canceled
                                                                 └─> unknown
取消路径： waiting_for_server ─> canceled
          goal_request_sent ─> cancel_pending ─> accepted
          accepted ─> cancel_request_sent ─┬─> cancel_accepted ─> canceled
                                           └─> cancel_rejected / cancel_error
回调异常： goal_response_error / result_error
同步发送失败： send_error
```

`accepted`、`waiting_for_server`、`goal_request_sent` 和 `cancel_*`（最终的 `canceled` 除外）是中间态，不是终态。成功率口径见 `README.md` 的「当前离线导航统计规则」：只有终态尝试进入分母，`preview` 不计入。

## 返航发送开关复核

发送路径不再是硬禁用，而是由 `enable_navigation_transmission` 守卫。复核两步：

默认值必须是关闭：

```bash
grep -n 'declare_parameter("enable_navigation_transmission"' \
  g3_integration_eval/g3_integration_eval/state_machine_node.py
```

输出应包含 `False`。

`send_goal_async()` 必须落在关闭分支的提前返回之后：

```bash
grep -n "_transmission_enabled\|send_goal_async(" \
  g3_integration_eval/g3_integration_eval/navigate_to_pose_client.py
```

`request_return()` 里的 `if not self._transmission_enabled:` 行号必须小于 `send_goal_async(` 的行号，即关闭态下发送不可达。

行为层面由单测固定：

```bash
python3 -m pytest test/test_navigate_to_pose_client.py -q
```

其中 `test_transmission_disabled_is_preview_only` 断言关闭态只产生 `preview`、`test_server_unavailable_does_not_send_goal` 断言 server 不可用时不发 goal。

## Domain 142 开启态验证（不接 Nav2 server）

这一步验证开启后的整条事件链，且**不会命令任何机器人**：Domain 142 上不启动 Nav2，action server 必然不可用，发送会停在 `server_unavailable`。绝不能在有真实 Nav2 的域上做这一步。

终端 A：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source /tmp/g3_eval_colcon/install/setup.bash
export ROS_DOMAIN_ID=142
ros2 run g3_integration_eval g3_state_machine --ros-args \
  -p enable_navigation_transmission:=true \
  -p navigation_server_timeout_sec:=1.0
```

启动日志应先出现 `NavigateToPose transmission ENABLED; ...` 的 warning。

终端 B（观察事件）：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source /tmp/g3_eval_colcon/install/setup.bash
export ROS_DOMAIN_ID=142
ros2 topic echo /g3/return_event std_msgs/msg/String
```

终端 C（触发返航）：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source /tmp/g3_eval_colcon/install/setup.bash
export ROS_DOMAIN_ID=142
ros2 topic pub --once /g3/command std_msgs/msg/String '{data: explore}'
bash g3_integration_eval/scripts/publish_test_battery.sh 0.19
```

预期结果：

1. 终端 B 先收到 `status=waiting_for_server`，约 1 秒后收到 `status=server_unavailable`，两条共享同一 `attempt_id`，`goal_id` 均为 `null`。
2. 终端 A 的 `server_unavailable` 事件走 error 级日志。
3. 该尝试进入成功率分母并计为失败，因此只跑这一步时返航成功率为 `0%`。这是预期行为（server 确实不可用），不是缺陷。

用 `record_bag.sh` 录包后，`evaluate_bag.py` 应能从这同一批事件算出 `return_success_rate`，而不是再报 `no_explicit_return_goal_marker`。
